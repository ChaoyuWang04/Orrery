# SkyRL-Agent：多轮 Agent 的 RL 先慢在 GPU 等 CPU，再卡在奖励全零

<!-- release-date: 2025-11-20 -->

> 本文依据 **SkyRL-Agent: Efficient RL Training for Multi-turn LLM Agent**，共同一作 Shiyi Cao 与 Dacheng Li，共 15 位作者，来自 NovaSky AI、UC Berkeley 与 Anyscale，arXiv:2511.16108v1，2025-11-20 提交，共 16 页（正文到 p. 13，其后为参考文献）。页眉全程标着 Work in Progress，没有独立的结论或限制章节。页码均指这份 PDF 自身的页码。文中区分三件事：**论文明确写了什么**、**我们如何解释它**、**哪些是外部资料或我们的计算**。

## 读前先把几个词说成人话

这篇论文一半是系统、一半是训练配方。先把会反复出现的词说清楚：

- **多轮长程 Agent（multi-turn, long-horizon agent）**：模型在真实环境里走很多步，每一步「看上下文 → 决定动作 → 环境给反馈」。修一个 GitHub bug 可能要看仓库、改文件、跑测试，来回几十轮。
- **Rollout（轨迹生成）**：让当前策略在一道题上完整跑一局，得到一条 **trajectory（轨迹）**。
- **POMDP（部分可观测马尔可夫决策过程）**：论文用它形式化多轮 Agent：第 $t$ 步看到上下文 $o_t$，按策略 $\pi_\theta(a_t\mid o_t)$ 选动作 $a_t$，拿到标量奖励 $r_t$。目标是整局回报的期望最大（PDF p. 3）：

  $$
  J(\theta)=\mathbb{E}_{\pi_\theta}\Big[\sum_{t=1}^{T} r_t\Big]
  $$

  $T$ 是这道题走了多少轮。
- **Dispatcher（调度器）**：决定一批轨迹里，哪一段活现在该跑。本篇系统贡献的核心。
- **Mask 式轨迹 与 Transition 式轨迹**：前者把整局对话拼成一条序列，工具返回的 token 打掩码不算梯度；后者把每一次模型调用单独记成 $(o_t,a_t,r_t)$ 三元组。
- **SWE-Bench Verified 与 Pass@1**：给真实仓库和一份 bug 报告，系统交出补丁，看项目单元测试过不过；Pass@1 是只出一次补丁就通过的比例。
- **AST（Abstract Syntax Tree，抽象语法树）**：把代码解析成树，按结构而不是按纯文本去搜。
- **ReAct**：让模型交替写推理和下工具调用的最简 Agent 脚手架。

三个训练后端的名字会反复出现，先摆正层级：

- **VeRL**：ByteDance 的 RL 训练框架，编程模型见 HybridFlow 一篇；
- **SkyRL-train**：同一团队的训练后端；
- **Tinker**：Thinking Machines Lab 的微调与采样 API，把分布式执行藏在接口后面（PDF p. 2）。

**SkyRL-Agent 不替代它们。** 它架在上面，负责生成、调度、记录多轮轨迹，再把数据交给其中任意一个后端去算优势、更新策略（PDF p. 2–3）。

## 一句话先说清

单轮数学 RL 里，一条轨迹几乎就是一次生成。多轮 Agent 里，一条轨迹至少有三段设备亲和性完全不同的活（PDF p. 4–5）：

1. **起环境**：起沙箱、装仓库、准备工具运行时，主要吃 CPU；
2. **跑 Agent**：模型生成吃 GPU，工具执行吃 CPU 或网络，交替进行；
3. **算奖励**：跑测试打分，又回到 CPU。

当时的 agent 训练框架把三段焊在同一个任务里，再按数据并行一起开，论文称之为 naive 异步批处理（PDF p. 4）。看上去已经异步了，GPU 却会周期性地空等。

论文给出两件事，一件解决「GPU 在等」，一件解决「梯度是零」：

- **流水线调度器**：把三段拆开，各排各的队，让这条轨迹的 CPU 活和另一条轨迹的 GPU 活叠在一起。生成阶段相对有界的 naive 异步批处理约 **1.55 倍**加速（PDF p. 1、p. 6）。
- **工具增强的训练配方**：给 SWE Agent 一个基于 AST 的搜索工具，让它先能找到该改的代码，稀疏的奖励才不至于整组全零。

两件合起来，用纯 RL、不蒸馏更强教师，把 Qwen3-32B 从 **24.4%** 训到 SWE-Bench Verified **39.4%** Pass@1，训练花 4601 个 H100 小时，是达到相近成绩的 DeepSWE（9180 H100 小时）的一半（PDF p. 1、p. 10）。

39.4% 要连同评测口径一起记：简化 ReAct 循环、只给 bash 和文件编辑器、40k 上下文、最多 100 步、每题只出一个补丁（PDF p. 1 脚注 1、p. 9–10）。

## 它在哪一层：Table 1 与同期框架

论文 Table 1 把当时的 agent 训练框架摆成五行（PDF p. 3）：

| 框架 | 训练后端 | Agent 执行 | 接口 | 运行时扩展 | 轨迹 |
|---|---|---|---|---|---|
| VeRL-Tool | VeRL | 数据并行 | Tool | Ray | Mask |
| rLLM | VeRL | 数据并行 | Gym | K8s | Mask / Transition |
| GEM | 多种 | 数据并行 | Gym | — | Transition |
| Agent-Lightning | 多种 | 数据并行 | — | — | Transition |
| SkyRL-Agent | 多种 | 数据并行 + 流水线（可扩展） | Tool | Ray / K8s | Mask / Transition |

论文对这几家的批评很具体（PDF p. 4）：

- 它们都停在 naive 异步批处理，也就是数据并行执行；
- Gym 风格的循环（rLLM、GEM）把 Agent 自己的状态放在 `env.step` 外面用临时代码管；
- Agent-Lightning 是训练后端与 LangChain、AutoGen 之间的中间层，缺少对自定义工具和新任务的原生支持；
- rLLM 与 VeRL-Tool 扩展性更强，但绑死在 VeRL 上；VeRL-Tool 只会 mask 式拼轨迹，难用于多智能体或会改写自己记忆的 Agent。

**我们如何解释它**：同样叫「异步」，卡的是不同的等待。AReaL 一类全异步系统拆的是「生成 GPU 与训练 GPU 互不等待」，代价是训练会吃到旧策略的数据。SkyRL-Agent 拆的是「同一批还在生成时，别让所有卡一起等环境初始化与测试」。它的 SWE 主实验训练本身是完全同策略（fully on-policy）的，训练 batch 等于 mini-batch（PDF p. 9）。两种异步正交，可以叠加，本篇只做了后一种。

## 先看全景：一条轨迹拆三段，transition 记完交给任意后端

![原文 Figure 2：任务数据集进入第 1 段运行时初始化，再进入第 2 段 Agent 运行（历史消息与工具在工具执行运行时上交替），然后进入第 3 段奖励计算；Agent 每次调用 llm.generate 的输入输出被 record_transitions 记进 transition 缓冲，post_process 再把它们与奖励合成训练数据，交给 SkyRL-train、VeRL 或 Tinker 的 adv_calc、forward_backward、optimizer_step（裁自原文 Figure 2，PDF p. 4）。](/reports/SkyRL-Agent/fig2-architecture.png)

图里有两条流。深蓝是 Agent 循环的数据流：观察进、命令出，走的是 K8s、Ray 或远程服务上的工具运行时。橙色是训练数据流：每次模型调用被装饰器记下，攒进缓冲，最后打包成后端要的格式。T1–T9 是九条轨迹，分别处在三个阶段里，调度器按策略把它们在三段之间倒手（PDF p. 4）。

系统由三块组成（PDF p. 2–3、p. 5）：

1. **以工具为中心的 Agent 循环**：动态注册工具、指令构造器和验证器，加新任务不改主循环；
2. **细粒度的异步调度器**：给「一批多阶段 rollout」提供统一的策略接口；
3. **后端桥**：把轨迹转成 SkyRL-train、VeRL 或 Tinker 要的输入。

下面按「为什么慢 → 调度怎么叠 → 工具怎么接 → 数据怎么交给后端 → SWE 配方怎么把分数打上去」往下走。

## 核心设计一：把一条 rollout 拆成三段，各排各的队

### 旧问题：整条轨迹当一个任务，GPU 跟着 CPU 一起等

引言把需求写成两层（PDF p. 2）：

- **轨迹内调度（intra-rollout）**：把一条 rollout 拆成起环境、生成、算奖励几段，各自独立调度，让它的 CPU 活能和别的轨迹的 GPU 活重叠；
- **轨迹间调度（inter-rollout）**：决定全局先后与优先级，让 CPU 与 GPU 的负载随时间保持平衡，缩短整批跑完所需的时间（makespan）。

现有框架把每条 rollout 当成一个不可拆的任务（PDF p. 2）。

### 新设计：三种调度策略，放在同一个接口下

![原文 Figure 3：三行时间轴。Async Batch 让四条轨迹同时从 INIT 开始；Async Batch (Bounded) 只允许两条并发，上一条算完 Reward 才开始下一条的 INIT，红框标出这段是 GPU 低利用期；Async Pipeline 在前两条还在生成时就提前做 INIT 2 到 INIT 5，Reward 挪到下方单独一行，与后续轨迹的 LLM 生成重叠（裁自原文 Figure 3，PDF p. 6）。](/reports/SkyRL-Agent/fig3-dispatchers.png)

调度器为每一段维护一个有界队列，按策略把作业送进去（PDF p. 5）。三种策略各有适用面（PDF p. 5–6）：

| 策略 | 怎么排 | 论文说它适合 |
|---|---|---|
| Async Batch | 所有轨迹一起开 | 起环境与算奖励都很轻的任务，如搜索增强推理 |
| Async Batch（Bounded） | 并发数封顶，一条跑完三段才补下一条 | 必须限流以免压垮运行时，或长寿命资源可以跨轨迹复用，如电脑使用任务的虚拟机 |
| Async Pipeline | 三条大小各自可配的有界队列，CPU 阶段与 GPU 推理重叠 | 起环境或算奖励很贵的任务，如 SWE |

Figure 3 里那段红框，就是有界批处理的病：上一波在算奖励、下一波在起环境，这段时间没有轨迹在用 GPU。Async Pipeline 把后面几条的 INIT 提前做掉，把 Reward 移出生成的关键路径。

**工作机制的要害是「有界」**。Async Pipeline 不是把并发开到最大。三条队列各有深度，既防 CPU 过载拖慢 Agent 循环，也防运行时服务被压垮（PDF p. 6）。Listing 2 展示了有界批处理的写法：一个信号量把并发卡在 `max_parallel_agents`（默认 8），每条轨迹依次 await 起环境、跑 Agent、算奖励三个函数（PDF p. 6）。新策略用 `@register_dispatcher` 注册即可。

论文还举了一个扩展方向：按评估代价做优先级调度，让测试用例多的轨迹先跑，免得它们成为拖尾、拉长整批时间（PDF p. 6）。这只是接口能力的举例，没有实测。

### 收益：生成阶段约 1.55 倍

![原文 Figure 1b：SA-SWE-32B 生成阶段的 GPU 利用率随时间变化，batch size 64、每题 8 条 rollout 共 512 条、2×8 张 H100。紫线（Async Pipeline）从开始到约 3200 秒一直稳在 90% 附近；蓝线（Async Batch Bounded）频繁掉到 50% 以下甚至归零，拖到约 5000 秒才结束，红色箭头标注 1.55× speedup（裁自原文 Figure 1b，PDF p. 1）。](/reports/SkyRL-Agent/fig1b-gpu-utilization.png)

正文的读法是：流水线下 GPU 利用率在整个生成阶段稳在约 90%；有界批处理的波谷，就是起环境与算奖励这类 CPU 活造成的 GPU 空等（PDF p. 6）。

**边界要说清**：

- 1.55 倍量的是**生成阶段**的墙钟，只在 SA-SWE-32B 这一组配置下测过（512 条轨迹、16 张 H100）。没有扫模型大小、集群规模或队列深度。
- 对照是**有界**批处理，不是无界的 Async Batch。对 SWE 这种重环境任务，无界全开会压垮运行时，所以有界才是现实的基线。
- 三条队列设成多大，论文没有给。队列深度成了新超参。

### 代价与反例：流水线不是永远更好

电脑使用那个案例用的是有界批处理，固定 32 个虚拟桌面（PDF p. 12）。虚拟机是长寿命资源，重置便宜，没有必要叠流水。调度策略是任务特性的函数，不是默认值。

### 可迁移启发

先画出自己这条流水里每一段吃什么设备，再决定并发展开在哪一层。数据并行解决的是「同一种活复制多份」，解决不了「三种活抢同一种设备」。准备和验收都重时，把它们从生成的关键路径上移开；都轻时，全开就够，硬上流水线只是多管几条队列。

## 核心设计二：工具当一等公民，连改自己的记忆也是一次调用

### 旧问题：Agent 状态被留在 env.step 外面

工具在运行时上分三类（PDF p. 2）：无状态的工具（Python 解释器）、改环境的工具（文件编辑器）、改 Agent 自身状态的操作（摘要、截断历史）。Gym 风格的循环里，第三类只能写在 `env.step` 外面的临时代码里（PDF p. 4–5），于是它不可学习，新任务一来还要改主循环。

### 新设计：Agent 只通过 OpenAI 风格的函数调用行动

每个工具自己实现执行逻辑、声明自己的运行时。已有的 Gym 环境把 `step()` 包成一个工具就能接进来（PDF p. 5）。Listing 1 是电脑使用任务的例子：`OSWorldActionTool` 的 `call()` 里直接调 `runtime.step(code, TIMEOUT)`（PDF p. 5）。

论文说这带来三件实事（PDF p. 5）：

1. Agent 状态和环境状态走同一套工具抽象，上下文管理这类操作也变得模块化、可学习；
2. 不同数据集绑不同的工具集与验证器，多个任务可以混在一个训练作业里；
3. 加新任务只要提供几个工具、一个任务专用的指令构造器和验证器。

### 错误分两类处理

真实环境里总会出问题：生成异常、工具调用格式错、超时、资源耗尽（PDF p. 7）。工具层已经把很多环境错误局部化了；Agent 循环再分两类（PDF p. 7–8）：

- **终止条件**：上下文窗口超了、到了最大步数，立刻结束这一局；
- **可恢复条件**：解析失败、参数不对，把纠正信息写回对话历史，让下一步自己改。

论文只定性说这能提高整体成功率，没有给前后对比。

**可迁移启发**：设计 Agent 运行时，先分清「哪些动作改世界、哪些动作改自己的记忆」。记忆操作如果只能写在循环外面，后面那种「摘要完把上下文重置」的 Memory Agent 就接不进 RL。

## 核心设计三：按 transition 记账，后端才能换

### 旧问题：「整局是一条连续文本」在多轮里经常是假的

短的工具增强推理里，常见做法是把整段对话拼成一条序列，工具返回的 token 打掩码（PDF p. 3）。多轮长程里，Agent 会在步与步之间做摘要、截断、选择性写入检索结果，交互历史本身是非平稳的（PDF p. 4）。这时 mask 式拼接很难推广。

### 新设计：每次模型调用记成一条 transition

一次模型调用及其反馈记成一条 transition，里面有输入 token、输出 token，以及推理端给出的对数概率（PDF p. 7）。记录靠一个装饰器完成，不改 Agent 逻辑：

```python
@record_transition
async def _generate(self, input_ids, sampling_params):
    return await self.backend.generate(input_ids, sampling_params)
```

论文列了三个好处（PDF p. 7）：

1. **缓解训推不一致**：显式记下采样时的对数概率，才能用 Flash-RL 这类方法校正推理引擎与训练引擎之间的数值错位；
2. **token 级保真**：token 进、token 出，避免「解码成文本再重新分词」造成的离策漂移。这里引的是 Agent Lightning 团队关于重新分词漂移的博客；
3. **算法更灵活**：可以动态摘要前文、插入结构化提示、甚至跨轮改 Agent 的角色。

效率上，共享同一前缀的 transition 仍会被打包成一条带掩码的训练样本。所以**执行中没改过上下文的轨迹，自然退回传统的拼接加掩码**（PDF p. 7）。transition 是超集，不是每一步都拆开算。

执行完后，`post_process` 输出一份与后端无关的中间格式：`prompt_token_ids`、`response_ids`、`logprobs`、`loss_masks`、`traj_rewards`、`traj_idx`、`rollout_metrics`（PDF p. 7，Listing 3）。从本地评测换到分布式训练，只改配置，不改 Agent 或任务代码。

论文把后端抽象的好处写成两句（PDF p. 7）：研究者可以在同一份任务上比较不同算法，去掉实现差异这个混淆项；同时保留各后端的强项，比如新模型支持、新算法、GPU / TPU / AMD 硬件、以及超大模型的 API 执行。

**我们如何解释它**：互操作在论文里是被三个小案例分别验证的：Deep Research 用 SkyRL-train，Memory Agent 用 Tinker，电脑使用用 VeRL（PDF p. 11–12）。SA-SWE-32B 主实验没写用的是哪个后端；也没有「同一任务换三个后端、结果仍可比」的实验。「换后端只改配置」目前是设计主张，不是测过的结论。

**可迁移启发**：执行层记账的粒度，决定你以后还能换哪些算法。只存拼好的文本，就只能做 mask 式的策略梯度；存下每次调用的 token 与对数概率，才能做摘要式上下文，才能校正训推不一致。

## SWE Agent：为什么训完整的交互循环

SWE-Bench 的设定是真实仓库加 bug 报告，产出补丁，看单元测试（PDF p. 8）。当时的解法分两家（PDF p. 8）：

- **Agent 系**（OpenHands、SWE-agent）：模型待在可执行环境里，用 shell、搜索、查看与编辑文件，反复看、改、构建、测，贴近真实开发；
- **Workflow 系**（Agentless）：规定死一条流水线，比如定位 → 修补 → 测试，把长程交互拆成一串可验证的单轮子任务，编排和评测更简单，代价是交互性与泛化。

论文站在前一家。它的假设是：在 SWE 里练出来的「有状态地用工具」能迁移到其他同样需要有状态工具交互的领域，所以端到端地训练完整循环（PDF p. 8）。后面 Terminal-Bench、BrowseComp-Plus、WebArena 三个评测就是为这个假设准备的。

## 训练配方一：先让 Agent 找得到代码，奖励才不是全零

![原文 Figure 1a：SA-SWE-32B 的四条训练曲线，横轴都是训练步（0–160）。左上奖励从约 0.18 升到约 0.40；右上是每批里一条都没修好的题数，SA-SWE-32B（紫）比 DeepSWE-stage1（橙）更低、降得更快；左下平均搜索次数从约 2.8 升到约 4；右下平均轮数从约 19 升到约 24（裁自原文 Figure 1a，PDF p. 1；DeepSWE 曲线取自其 wandb 日志）。](/reports/SkyRL-Agent/fig1a-training-metrics.png)

### 旧问题：找不到该改的地方，整组轨迹拿一样的 0 分

论文观察到，SWE Agent 常卡在**错误定位**上（PDF p. 8）：

- 过度依赖直接查看文件，不爱用 `grep`、`find`；
- 即使搜，也不会把查询收成有信息量的模式或关键词，反复找不到；
- 退回一块一块地翻文件，或一次拉回大量无关内容，把上下文耗光。

长程任务的奖励又是稀疏且延迟的。论文给了一个数：只给 bash 的最小工具集（Mini-SWE-Agent 的设置）在 R2E-Gym 数据上，未解决的比例高达 50/64（PDF p. 8）。

**我们如何解释它**：训练 batch 正好是 64 道题，每题 8 条 rollout（PDF p. 9）。如果 64 道题里 50 道的 8 条轨迹全失败，这 50 组里没有谁比谁好，组内相对优势全是零，RL 等于只在剩下 14 道题上学。Figure 1a 右上的纵轴也叫「一条都没修好的题数」，SA-SWE-32B 起步时约 36，读自该图；论文没有明说它和 50/64 是同一口径，但两者放在一起看，工具把起点的全零组从约八成（50/64）降到了五成多（约 36/64），后半句是我们的推断。

### 新设计：AST 搜索工具，结果末尾附上下一步提示

他们实现了一个基于 AST 的搜索工具，支持模糊匹配与结构模式搜索，灵感来自 LocAgent（PDF p. 8）。为了把策略往「去搜」而不是「去翻」推，每条搜索结果末尾追加提示，建议下一步搜哪些词或模式（PDF p. 8）。

论文说这些工具增强对高效 RL 是关键：没有它们，端到端 RL 因奖励稀疏而极其困难；有了它们，只训 125 步就追平甚至超过同规模的前作（PDF p. 8–9）。训练中平均搜索次数从 3 升到 4，平均轮数从 18 升到 25（PDF p. 11）。

### 评测时把搜索工具拿掉了

为了看泛化，评测时把搜索工具去掉（PDF p. 9）。论文说模型表现出「内化的搜索行为」，没有专用搜索工具也拿到「相当」的成绩。

**边界要说清**：

- 「相当」没有给出去掉工具前后的 Pass@1 对照数字；
- 摘要里说工具能提高 rollout 的 Pass@K（PDF p. 1），全文没有一张 Pass@K 的表或图；
- 没有工具消融，所以 24.4 → 39.4 这 15 个点里多少归 AST 搜索、多少归调度器、多少归训练期提示，分不开。

### 可迁移启发

奖励稀疏的长程 RL，先别问损失函数，先问「整组全错的题占多少」。工具、提示、课程都是在给 rollout 的 Pass@K 抬底。底太低时，换哪种优势估计都救不了零梯度。DAPO 用动态采样把全对全错的组过滤掉；这里是先让「全错」变得没那么全。两者是同一类病的两种药。

## 训练配方二：完全同策略、留一法优势、超长只挡梯度

超参全部来自 PDF p. 9：

| 项目 | 取值 |
|---|---|
| 基座 | Qwen3-32B；改了聊天模板，保留前几轮的 thinking |
| 数据 | R2E-Gym 的 4.5K 条实例，纯 RL，无 SFT，不蒸馏更强教师（PDF p. 3、p. 9） |
| batch | 训练 batch 与 mini-batch 都是 64，论文称为完全同策略 |
| 每题 rollout | 8 条 |
| 训练时上限 | 32K token 上下文、50 轮；撞到上限的轨迹从梯度里掩掉 |
| 优势估计 | 留一法（leave-one-out），去掉标准差归一化与长度归一化 |
| KL 与熵损失 | 都关掉 |
| 学习率 | $1\times 10^{-6}$ |
| 评测检查点 | 第 125 步（PDF p. 1，Figure 1a 图注） |

**「完全同策略」的操作定义很窄**：训练 batch 等于 mini-batch，一批 rollout 只做一次梯度更新。DAPO 一篇的做法相反，一轮 rollout 切成多次更新。两边都叫同策略，一步里参数动几次不是一回事。

**留一法优势**：同一道题的 8 条轨迹里，每条的基线是其余 7 条的平均奖励。论文只写了 following DeepSWE 与 Dr. GRPO 两篇（PDF p. 9），没有写公式，也没有单独消融；KL 与熵损失为什么关也没解释。

**超长只挡梯度，不改奖励**（PDF p. 9）：撞到 32K 或 50 轮上限的轨迹，奖励和优势照常算，只是不进入梯度。目的是别让模型被训练成「讨厌动作多、推理长的轨迹」。

**我们如何解释它**：这和 DAPO 一篇里的超长过滤是同一招，都是把被截断样本的损失屏蔽掉，拆开「解法质量」与「撞到资源上限」。不同在于 DAPO 最终给出的方案是在长度上限前加一段软惩罚，改的是奖励；这里明说奖励与优势都不改，截断轨迹仍按原奖励留在组内基线里。论文没有报告被掩掉的轨迹占多少。

**训练量的量级**：125 步 × 64 题 = 8000 次抽题，约是 4.5K 题库的 1.8 遍；再乘 8 条 rollout，约 6.4 万条轨迹。这是我们的计算，论文没写。

### 训练期提示：把 Agent 从死胡同里拽回来

多轮 Agent RL 常卡在重复或无效的行为上（PDF p. 9）：不调工具、函数调用写错或不写、反复做同样没进展的动作、忘了任务还剩几步、没到上限就提前收工。SWE-Gym 与 Kimi-Dev 都报告过，从通用预训练模型出发会有这类脆弱行为。

他们在**训练时**注入结构化提示（PDF p. 9）：工具执行失败时建议下一步可试的动作；步数预算或上下文快用完时发通知；函数调用不合法或不完整时给纠正；编辑失败时提示回头检查。论文说这些提示显著提高轨迹质量、稳住 rollout 收集、增加成功轨迹在策略更新里的比例。

**原文没写的**：没有提示的消融数字；也没写评测时提示是否还开着。评测用的是只给 bash 和编辑器的简化 ReAct（PDF p. 9），按这个描述，评测侧大概率没有这套提示，但论文没有写死。

**可迁移启发**：提前收工和死循环不会报错，只会让成功轨迹变少。结构化提示本质上是提高有效样本率，和工具增强同属一类：在奖励函数之外给探索铺路。

### 读这张表要按层读

**第一层，同一套 Simple ReAct。** 基座 24.4，SA-SWE-32B 39.4，涨 15.0 个点（我们的计算）。同规模同脚手架下，蒸馏 Claude 的 SWE-agent-LM-32B 是 38，纯 RL 的 DeepSWE 是 36.4。论文据此说它是同规模「开放配方」模型里的最好成绩（PDF p. 9）。

**第二层，别漏掉 Qwen3-Coder-30B。** 它在同一套 Simple ReAct 下是 45.0，比 SA-SWE-32B 高 5.6 个点（我们的计算）。论文把它放在「参考」一栏，不和开放配方比。**我们如何解释它**：纯 RL 把一个通用 32B 在最小工具集上抬了 15 个点，仍没追上专门的 coder 基座。

**第三层，「原文自报」一列不能拿来给谁加分。** DeepSWE 在自家脚手架上是 42.2，换到 Simple ReAct 是 36.4，光换脚手架就差 5.8 个点（我们的计算）。SWE-Swiss 与 Kimi-dev 是在 Agentless 脚手架下训的，论文说它们在 ReAct 里很难遵循工具调用指令，分数远低于原文，所以只列自报分数（PDF p. 10）。Kimi-dev 还是 72B。

**第四层，成本。** 摘要写「超过 2 倍」的成本下降（PDF p. 1），第 4.3 节写「低 50%」（PDF p. 10），表上是 4601 对 9180；$9180/4601\approx 1.995$，是我们的计算。DeepSWE 用的是同一份 4.5K R2E-Gym、同样纯 RL、默认 R2E-Gym 脚手架（PDF p. 9）。SWE-agent-LM-32B 则是在 Qwen2.5-Coder-32B-Instruct 上用 Claude 3.7 Sonnet 生成的 5016 条 SWE-smith 轨迹微调的（PDF p. 9），没有报花费。

**1.55 倍和一半成本不要合成一个故事。** 前者是生成阶段相对有界批处理的加速；后者是整次训练相对 DeepSWE 的花费，里面至少叠了调度器、AST 工具、训练期提示，以及「125 步就停」。论文把 SA-SWE-32B 的未解决曲线画得比 DeepSWE 更低、降得更快（PDF p. 10，Figure 1a），但 DeepSWE 的曲线取自其 wandb 日志，不是作者复跑（PDF p. 1）。

### 跨任务泛化：方向一致，幅度几个点

只在 SWE 上训练，拿去评三个别的 Agent 基准（PDF p. 10，Table 3）：

| 模型 | Terminal-Bench | BrowseComp-Plus 准确率 | BrowseComp-Plus 平均轮数 | WebArena |
|---|---:|---:|---:|---:|
| Qwen3-32B | 13.75 | 18.1 | 3.68 | 15.8 |
| SA-SWE-32B | 16.25 | 19.4 | 4.6 | 17.0 |

三个基准各测什么（PDF p. 10）：

- **Terminal-Bench 0.1.1**：80 道命令行里的系统级任务，覆盖软件工程、系统管理、安全等；评测用 OpenHands agent（脚注 3），不是 SWE 那套简化 ReAct；
- **WebArena**：812 道真实感网站上的多步浏览器任务，覆盖电商、论坛、协作软件、内容管理；
- **BrowseComp-Plus**：830 道题，在一份人工核实、带困难负例的固定语料上多步检索与推理；检索器是 Qwen3-Embedding-8B，搜索返回前 5 条。

相对基座分别涨 2.5、1.3、1.2 个点（我们的计算）。论文特别点了 BrowseComp-Plus：模型只在 SWE 上训过，却比基座调用了更多次搜索（PDF p. 11）；配合训练中搜索次数 3 → 4、轮数 18 → 25，论文的读法是模型学会了「更依赖外部搜索、更愿意多走几步」。

**边界**：三个基准都只和基座比，没有和 DeepSWE 或 Qwen3-Coder 比；Terminal-Bench 换了 OpenHands 脚手架。泛化存在，强度是几个点，不是「换领域仍领先」。

## 另外三个 Agent：每个换一个后端，规模都小

第 5 节的目的是证明框架能接不同任务、不同后端，不是再刷一个主结果。三个案例都是 Qwen3-8B 量级。

### Deep Research × SkyRL-train

工具是 SerperAPI 搜索加 Jina Reader 取网页，外加缓存与两段式摘要：长网页切块、分块摘要、合并时保留引用（PDF p. 11）。

数据从 MegaScience 抽 5 万题，用 Qwen3-8B（thinking 模式）每题滚 4 次离线估难度，按成功次数分成 0/4 到 4/4 五档；再照 Polaris 的镜像难度分布配成 25% 不可能、30% 难、30% 中、15% 易，并在计算机、生物、物理、经济之间平衡（PDF p. 11）。训练用 GRPO 与 General-Reasoner 的通用验证器，全局 batch 64、每题 8 条 rollout、mini-batch 64、学习率 $5\times 10^{-6}$，摘要模型是非推理模式的 Qwen3-235B（PDF p. 11）。

评测在 HLE-500 上用 LLM 当裁判。通用验证器偏宽松，所以另用 gpt-oss-20b 当主裁判（PDF p. 11）：

| 裁判 | 训练前 → 后 |
|---|---|
| 通用验证器 | 12.6% → 18.8% |
| gpt-oss-20b | 9.2% → 10.2% / 11.0% |

斜杠两侧 10.2% 与 11.0% 各指什么，论文没解释。宽松裁判涨 6.2 个点，严裁判只涨 1–2 个点（我们的计算）。

论文记下的两条工程教训，比这几个点更有用（PDF p. 11–12）：

1. **重工具供给不足会直接污染奖励。** 网页抓取每请求约 10k token，配 Qwen3-32B 当摘要器，单张 H200 上每迭代 2101.6 秒；换成 Qwen API 降到 592.1 秒，约 3.5 倍。最终用四张 GH200 加数据并行路由。供给不够时超时会污染 rollout，第 30 步附近出现一次奖励凹陷，30–33 步才恢复。对策是给足工具容量，并把异常轨迹掩掉。
2. **在线搜索会泄露基准答案。** 在 GPQA-Diamond 上评测时，模型有时直接从 Hugging Face 等公开页面检索到题解。他们因此屏蔽 Hugging Face、GitHub、GitLab、Chegg 这类域名。

### Memory Agent × Tinker

这是给「为什么要 transition 而不是 mask」准备的例子。MemAgent 递归地读长文，把内容摘要进固定大小的记忆。本篇把它实现成一个 **Next 工具**：对当前块写摘要，然后把上下文重置成只含摘要，再给下一块（PDF p. 12，Figure 6a）。

数据是 RULER-HotpotQA，一段金标支持段落加若干干扰段；每块至多 4k token，训练看到至多 28k，评测到 112k；验证器是 GPT-5-nano（PDF p. 12）。模型是非 thinking 模式的 Qwen3-8B，Tinker 后端，LoRA rank 128，batch 32，8 条 rollout，每轮至多 8K token（PDF p. 12）。

对照写的是 MemAgent 原文：Qwen2.5-7B-Instruct、batch 128、组大小 16、精确匹配验证器，准确率 79.69%（PDF p. 12）。**本篇没有报告自己这次训练的最终准确率**，只给了 Figure 6b 的奖励与验证曲线，两条都在涨。它证明的是「会改写上下文的脚手架接得进框架」，不是「超过了 MemAgent」；两边模型、验证器、batch 都不同。

### Computer Use × VeRL

OSWorld 虚拟桌面，动作是模型写 PyAutoGUI 代码，反馈是无障碍树，整个环境包成 Listing 1 那个工具（PDF p. 12）。数据少，所以照 ARPO（一篇 GUI Agent 的经验回放工作）的做法，从基准里筛出 32 道难、中、易的题当训练集。调度用有界批处理，固定 32 个虚拟桌面，虚拟机作为 Ray 远程任务拉起，把 CPU 上的环境反馈与 GPU 上的生成分开。训练 batch 8，每题 8 条 rollout，奖励由环境自带的评价函数给（PDF p. 12–13）。

**这是全文最坦白的负结果**：训练奖励稳步上升，验证准确率几乎不涨（PDF p. 13）。论文的判断是这些任务对 Qwen3-8B 本身就太难，学到的策略出不了训练环境；ARPO 也报告过类似趋势。Figure 7 只画了奖励曲线。

三个案例合起来，互操作被验证的方式是「每个后端接一种任务」。电脑使用那个案例还说明：框架能跑，不等于小模型在 GUI 任务上能泛化。

## 纯 RL、不蒸馏：它成立的前提比口号窄

论文反复强调 SA-SWE-32B 纯 RL、不靠更强教师（PDF p. 1、p. 9）。Table 2 也把它和「Claude 蒸馏」「R1 蒸馏 + RL」分开了。但这句话有几条前提，论文有的写了，有的要前后拼：

1. **起点不是基座模型。** 用的是 Qwen3-32B，还改了聊天模板保留前几轮 thinking（PDF p. 9）。这是已经会对话、会思考的模型，不是从零冷启动。
2. **工具与提示是学习信号的一部分。** 只给 bash 时未解决率到 50/64，论文说端到端 RL「极其困难」（PDF p. 8）。纯 RL 省掉的是 SFT 轨迹和教师，没有省掉「把探索空间修到 RL 能吃」这一步。
3. **评测脚手架比训练更穷。** 训练有搜索工具，评测拿掉；训练 50 步、32K，评测 100 步、40K。39.4% 不是训练那套循环的分数。
4. **同最小工具集下，通用 32B 加 RL 仍低于 30B coder 基座的 45.0。**
5. **换到 GUI，8B 上奖励涨、验证不涨。**

## 读完要留下的判断

**被实验撑住的：**

- 在 SA-SWE-32B 这组配置下，流水线调度把生成阶段缩短约 1.55 倍，GPU 利用率稳在约 90%（PDF p. 6，Figure 1b）。
- 同一套 Simple ReAct 下，纯 RL 把 Qwen3-32B 从 24.4 训到 39.4，高于同规模的 DeepSWE（36.4）与 SWE-agent-LM-32B（38），花费约是 DeepSWE 的一半（PDF p. 10）。
- 只训 SWE，三个别的 Agent 基准都涨了 1–3 个点（PDF p. 10）。

**只是作者观察或设计主张的：**

- AST 搜索与训练期提示「至关重要」：没有消融。
- 去掉搜索工具后成绩「相当」：没有数字。
- 换后端只改配置：三个案例各用一个后端，没有同任务多后端对照。

**原文没公开的：** 三条队列的深度；SA-SWE 主实验用的后端；被超长掩掉的轨迹比例；Memory Agent 的最终准确率。

## 可迁移启发

1. **先画设备亲和性，再决定并发。** 起环境、生成、算奖励吃的是不同设备。把一条 rollout 当成不可拆的任务，是默认设置，不是物理定律。
2. **异步有两个正交的轴。** 训练与生成之间的异步会引入旧策略数据；rollout 内部三段之间的异步不会。本篇在完全同策略下拿到了 1.55 倍，说明后一种可以先做、而且没有离策代价。
3. **有界比无界更现实。** 重环境任务里，队列深度要防 CPU 过载，也要防把运行时服务打垮。
4. **记账粒度决定算法空间。** 存每次调用的 token 与对数概率，才能做摘要式上下文和训推校正；没改过上下文时还能退回拼接加掩码，不吃亏。
5. **零梯度先治底。** 整组全错时，先用工具、提示、课程把 Pass@K 抬起来，再谈优势估计。
6. **截断只挡梯度。** 撞上步数或上下文上限的轨迹，不等于做错了；奖励照算、梯度不回传。
7. **分数要连同脚手架报。** 同一个 DeepSWE，换脚手架就差 5.8 个点。比较模型前先问脚手架。
8. **重工具的供给是奖励质量的一部分。** 摘要器算力不够导致超时，会直接在奖励曲线上砸出凹陷；在线搜索还会把答案搜回来。

## 关键词回看

- **Async Batch / Async Batch（Bounded） / Async Pipeline**：三种调度策略；后者用三条有界队列让 CPU 阶段与 GPU 推理重叠，SWE 生成阶段约 1.55 倍（PDF p. 5–6）。
- **轨迹内调度 / 轨迹间调度**：前者拆阶段，后者排全局顺序与优先级（PDF p. 2）。
- **以工具为中心的 Agent 循环**：Agent 只通过 OpenAI 风格函数调用行动，改环境、改记忆、无状态工具走同一接口（PDF p. 5）。
- **Transition**：每次模型调用记下输入、输出 token 与对数概率；共享前缀时再打包回拼接加掩码（PDF p. 7）。
- **post_process**：输出与后端无关的中间格式，交给 SkyRL-train、VeRL 或 Tinker（PDF p. 7）。
- **AST 搜索工具**：按代码结构做模糊与模式搜索，结果末尾附下一步提示；评测时拿掉（PDF p. 8–9）。
- **完全同策略**：训练 batch 等于 mini-batch，都是 64（PDF p. 9）。
- **留一法优势**：组内每条轨迹以其余轨迹的平均奖励为基线，去掉标准差与长度归一化（PDF p. 9）。
- **Simple ReAct**：只给 bash 与文件编辑器、40K 上下文、最多 100 步、每题一个补丁；39.4% 只在这个口径下成立（PDF p. 9–10）。
- **SA-SWE-32B**：Qwen3-32B 纯 RL 得到的 SWE Agent，4601 H100 小时（PDF p. 10）。

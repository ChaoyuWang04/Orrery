# DeepSeek-OCR：一千个字，最少要几个视觉 Token

<!-- release-date: 2025-10-20 -->

> 本文依据 DeepSeek-AI 的 **DeepSeek-OCR: Contexts Optical Compression**，arXiv:2510.18234v1，2025-10-21 提交，共 22 页（正文到 p. 19，其后是参考文献）。页码均指 PDF 自身页码。文中区分三件事：**报告明确写了什么**、**我们怎么解释它**、**哪些是外部资料或本文推算**。

## 读前先把几个词说成人话

- **Token（词元）**：模型处理序列的最小单位。文字切成 text token，图像切成 vision token。两种 token 进同一个解码器，占同样的序列位置，付同样的注意力代价。
- **OCR（Optical Character Recognition，光学字符识别）**：把图片里的文字读成可编辑的文本。在这篇报告里，它不是目的，而是一把尺子。
- **VLM（Vision-Language Model，视觉语言模型）**：「视觉编码器 + 语言解码器」两段式的模型。
- **窗口注意力 / 全局注意力**：窗口注意力只让每个位置和邻近的一小片互相看，代价随序列长度近似线性增长；全局注意力让所有位置两两互看，代价随长度平方增长。
- **激活显存（activation memory）**：前向计算时必须暂存的中间结果。它和参数量是两本独立的账，高分辨率图像常常先爆在这里。
- **压缩率（compression ratio）**：报告定义为「标准答案的 text token 数 ÷ 模型用掉的 vision token 数」（PDF p. 1，Figure 1 图注）：

$$
\text{compression} = \frac{N_{\text{text}}}{N_{\text{vision}}}
$$

10× 的意思是：1 个视觉 Token 顶了 10 个文本 Token。

## 先说矛盾：文本 Token 太贵，图像凭什么更便宜

大模型读长文本贵，贵在注意力：序列长度为 $L$ 时，两两比较的次数随 $L^2$ 增长。报告开篇就把问题定在这里（PDF p. 3）。过去几年的主流解法——稀疏注意力、线性注意力、压缩 KV Cache——有一个共同前提：输入必须是一串文本 Token，只能在序列内部动手脚。

DeepSeek-OCR 换了一个问法：**为什么一定要用文本 Token 来装文本？**

一张写满字的页面，人眼一扫就知道有上千个字，但在模型眼里它可能只占一百个 vision token。报告的原话是：一张包含文档文字的图像，能用远少于等价数字文本的 Token 表示丰富信息（PDF p. 3）。

于是问题变得可以量化。报告在相关工作一节把它写成一个研究问题：**对一份包含 1000 个词的文档，最少需要多少个 vision token 才能解码出来？** 报告说，当时的模型都没有回答过这个问题（PDF p. 4）。

## 一句话先说清

DeepSeek-OCR 是一个 OCR 模型，但它想证明的不是 OCR。它想证明：**把文字渲染成图像、再用视觉 Token 表示，是一条可行的上下文压缩路线，而且这条路线的「压缩多少、丢多少」可以测出来。**

报告给出的测量结果（PDF p. 1、p. 3）：

- 压缩率在 10× 以内，OCR 解码精度约 97%；
- 9–10× 时 96% 以上，10–12× 时约 90%；
- 压到约 20×，精度仍有约 60%。

为了做这个测量，报告造了三样东西（PDF p. 3、p. 5–7）：

1. **DeepEncoder**：一个约 380M 参数的视觉编码器，高分辨率下激活显存低、吐出的 vision token 少；
2. **多分辨率模式**：同一份权重可以吐出 64 到一千多个 vision token，把压缩率变成一个能扫的自变量；
3. **DeepSeek-3B-MoE 解码器**：总参数 3B、每个 Token 只激活约 570M，用来证明「连这么小的解码器都学得会解压」。

顺带地，这个模型在真实文档解析上也很强，还能当数据工厂用（PDF p. 1、p. 3）。

如果只记一句：

> **把长文本渲染成图，是把「一维序列压缩」换成「二维有损编码」；而有损编码的分辨率旋钮，天然可以做成分级的。**

## 为什么用 OCR 当尺子

「视觉能压缩文字」只是直觉，要变成数字，就得回答：**压缩之后信息还剩多少？**

普通的看图问答量不出来：答对一道题，只说明模型抓住了与这道题相关的那部分。OCR 不一样，报告说它在视觉与语言之间建立了天然的「压缩—解压」映射，还自带可量化的指标（PDF p. 3）。拆开看，它恰好满足三条：

1. **有标准答案**：原文已知，可以逐字比对；
2. **是全量还原**：整页都要吐出来，漏哪段都扣分；
3. **压缩和解压是同一件事的两端**：渲染即编码，识别即解码。

报告自己也没把 OCR 当终点。结论一节写明：单靠 OCR 不足以完整验证真正的上下文光学压缩（PDF p. 19）。这条边界贯穿全文。

## 旧路堵在哪：三类视觉编码器

报告的 Figure 2 画了当时开源 VLM 常用的三类视觉编码器，每类都标了缺陷（PDF p. 4）：

| 路线 | 图上举的代表 | 做法 | 图上标出的缺陷 |
|---|---|---|---|
| 双塔 | Vary、DeepSeek-VL | 并联一个 SAM 编码器处理 1024 高分辨率，扩充视觉词表 | 不支持流水线并行；需要两套预处理；不支持极端分辨率；难部署 |
| 切片 | InternVL 系列、DeepSeek-VL2 | 把大图切成 384 的小块并行编码，块数常超过 15 | 原生分辨率低；块太碎；vision token 太多；全局视野小 |
| 自适应分辨率 | Qwen2 / 2.5 / 3-VL 系列（NaViT 范式） | 不切片，整图按 patch 编码，token 数 = 宽 ÷ 14（或 16）× 高 ÷ 14（或 16） | vision token 太多；训练需要超长序列；激活显存大；推理慢 |

值得注意的是，前两类的代表里就有 DeepSeek 自己的上一代 VLM。三条路其实卡在同一个矛盾上：**要看清小字就得高分辨率；分辨率一高，patch 就多；patch 一多，要么 vision token 爆炸，要么激活显存爆炸。**

报告因此列出它需要的编码器五条件：能吃高分辨率、高分辨率下激活低、vision token 少、支持多种分辨率、参数量适中（PDF p. 5）。现成的开源编码器没有一个同时满足，所以自己造。

**我们如何解释它。** 第三条和第四条是研究目标逼出来的：要画压缩率曲线，vision token 必须又少、又可调。DeepEncoder 首先是一台测量仪器，其次才是一个通用编码器。

也要标一个边界：报告**没有**把 DeepEncoder 和这三类编码器放在同一条件下做对照。Figure 2 的叉号是设计论述，不是实测。

## DeepEncoder：贵的那段只处理短序列

![DeepEncoder 的 token 流：1024×1024 输入切成 4096 个块，先由冻结的 SAM-base 用窗口注意力处理，再经两层卷积压成 256 个 token，只有这 256 个进入可训的 CLIP-large 全局注意力，最后交给 3B MoE 解码器。](/reports/DeepSeek-OCR/figure-deepencoder-tokens.svg)

### 结构：三段串联

DeepEncoder 约 380M 参数，三段串联（PDF p. 5）：

1. **SAM-base**（patch 大小 16，80M），以窗口注意力为主，负责「视觉感知」特征；
2. **卷积压缩器**：借自 Vary，两层卷积，每层 kernel 3、stride 2、padding 1，通道 256 → 1024，合计把 token 数降 16 倍；
3. **CLIP-large**（300M），密集全局注意力，负责「视觉知识」特征。CLIP 的第一层 patch embedding 被删掉，因为它的输入已经不是图像，而是上一段吐出的 token。

跟着 token 数走一遍（PDF p. 5–6）：

$$
1024 \times 1024 \xrightarrow{\ \text{patch } 16\ } 64 \times 64 = 4096 \xrightarrow{\ \text{卷积 } 16\times\ } 256
$$

报告的解释是：前半段以窗口注意力为主、只有 80M，处理 4096 个 token 的激活可以接受；进入全局注意力之前已经压到 256，整体激活显存就可控了（PDF p. 5–6）。

**我们如何解释它。** 全局注意力的两两配对数随 token 数平方增长：$4096^2 \approx 1678$ 万，$256^2 = 65536$，相差 256 倍（本文推算）。压缩器必须夹在两段中间、放在昂贵的那一段之前；反过来先跑全局注意力再压缩，平方项一分都省不掉，压缩器只剩「少给解码器几个 token」的作用。

### 前半段被当成分词器

训练一节有个很能说明设计意图的细节（PDF p. 10）：整个模型按流水线并行切成 4 段——

- **SAM + 压缩器**被当作「视觉分词器」（vision tokenizer），放在 PP0，**参数冻结**；
- **CLIP** 被当作「输入嵌入层」（input embedding layer），放在 PP1，参与训练；
- 解码器 12 层，PP2、PP3 各放 6 层。

**我们如何解释它。** 这是一个好用的心智模型：把含混的「视觉编码器」拆成「不学习的切分规则」和「可学习的表示映射」两半，再分别决定冻不冻。

### 代价与边界

- **没有结构消融。** 串联对并联、16× 对 8× 或 32×、SAM + CLIP 对其他骨干组合，报告都没做对照；我们只知道这个组合能工作，不知道它是不是最优。
- **冻住 SAM**，感知能力的上限就由 SAM 的预训练决定。报告选它是为了「受益于既有工作的预训练」（PDF p. 5），这既是收益也是天花板。
- **卷积是固定倍率的均匀降采样**，不看内容。密集小字和大标题被压掉的概率一样。这是我们从结构推出的判断，报告没有讨论。
- **没有激活显存的实测数**。「低激活」「可控」只有定性描述。

**可迁移启发**：流水线里有一段代价随规模平方增长时，先别去优化它的常数，而是问：能不能在它前面放一个降采样，让平方项作用在更短的序列上。

## 多分辨率：把压缩率做成模型的一个档位

### 为什么必须支持多分辨率

要回答「一千个字要几个 vision token」，就得能连续地调 vision token 数（PDF p. 6）。每个预算训一个模型，成本高，各点也不可比。所以 DeepEncoder 用**位置编码的动态插值**支持多种分辨率，多个模式**一起训练**，一份权重覆盖所有档位（PDF p. 6）。

Table 1（PDF p. 6）：

| 模式 | Tiny | Small | Base | Large | Gundam | Gundam-M |
|---|---:|---:|---:|---:|---|---|
| 分辨率 | 512 | 640 | 1024 | 1280 | 640 局部 + 1024 全局 | 1024 局部 + 1280 全局 |
| vision token | 64 | 100 | 256 | 400 | $n \times 100 + 256$ | $n \times 256 + 400$ |
| 预处理 | 缩放 | 缩放 | 补边 | 补边 | 缩放 + 补边 | 缩放 + 补边 |

原生四档的 token 数都等于 $(\text{边长}/64)^2$：边长先被 patch 16 切一次，再被卷积压 4 倍边长（本文验算）。

### 直接缩放与补边：两种取舍

Tiny 和 Small 本来就小，报告选择**直接缩放到目标尺寸，不保长宽比**，免得补出来的空白浪费 token（PDF p. 6）。

Base 和 Large 反过来，**补边保住原始长宽比**。补出来的区域不带信息，所以报告给了一个有效 token 的折算公式（PDF p. 6，式 1）：

$$
N_{\text{valid}} = \left\lceil N_{\text{actual}} \times \left( 1 - \frac{\max(w,h) - \min(w,h)}{\max(w,h)} \right) \right\rceil
$$

$w$、$h$ 是原图宽高，$N_{\text{actual}}$ 是这一档的名义 token 数。意思很朴素：图越接近正方形，补边越少，有效 token 越接近名义值。Figure 4 上的简写 $R = 1 - (H - W)/W$ 分母与式 1 不同，以式 1 为准（PDF p. 6）。

Table 3 里 Base 标 256(182)、Large 标 400(285)，括号里就是在 OmniDocBench 上按式 1 算出的平均有效 token 数（PDF p. 11）。报告在报「用了多少 token」时，报的是折过水分的数。

### Gundam：给超大版面加一层瓦片

报纸这样的版面塞不进 1280×1280，于是有了动态分辨率的 Gundam 模式（PDF p. 7）：

- $n$ 个 640×640 的局部瓦片，每个出 100 个 token，加一个 1024×1024 的全局视图出 256 个，合计 $n \times 100 + 256$；
- 切法沿用 InternVL2.0，$n$ 控制在 2–9；宽高都小于 640 时 $n = 0$，退化成 Base；
- 报告说切瓦片相当于「第二层窗口注意力」，能再降激活；又因为原生分辨率高，瓦片不会切得太碎。

这句话正好回应了前面对切片路线的批评：**同样是切片，原生分辨率高，切得就少。**

Gundam-master（1024 局部 + 1280 全局）**没有和其他档一起训**，而是在训好的 DeepSeek-OCR 上用 6M 条采样数据续训出来的，理由是它分辨率太大，混在一起会拖慢整体训练（PDF p. 7、p. 9）。所以它和其他档不是严格意义上的同一次训练。

**可迁移启发**：要研究某个变量对效果的影响，先问它能不能变成模型的一个输入条件。一份权重扫完整条曲线，既省算力，也消除了跨模型对比的混淆。

## 解码器：只让 570M 参数干活

解码器是 DeepSeek-3B-MoE：每个 Token 从 64 个路由专家里激活 6 个，外加 2 个共享专家，激活参数约 570M（PDF p. 7）。报告的理由是它兼有 3B 模型的表达力和 500M 小模型的推理效率，很适合 OCR 这种领域集中的研究（PDF p. 7）。细粒度专家加共享专家的排布，见 DeepSeekMoE 一篇。

解码器的任务被写成一行（PDF p. 7，式 2）：

$$
f_{\text{dec}}: \mathbb{R}^{n \times d_{\text{latent}}} \rightarrow \mathbb{R}^{N \times d_{\text{text}}}, \qquad \hat{X} = f_{\text{dec}}(Z), \quad n \le N
$$

$Z$ 是 DeepEncoder 吐出的 $n$ 个视觉 token，$\hat{X}$ 是重建出的 $N$ 个文本表示。**$n \le N$ 是全篇的中心**：输入比输出短，解码器做的是解压。

报告接着说，这个非线性映射「可以被紧凑的语言模型通过 OCR 式训练有效学到」，并「有理由推测」更大的 LLM 经过针对性预训练会更自然地具备这种能力（PDF p. 7）。

后半句是推测（conjecture），不是实验。它的逻辑是一个下界论证：570M 激活参数都学得会，更大的模型没理由学不会。这保证了可学性，但不保证更大模型能把压缩率推得更高。

**可迁移启发**：想证明一个映射「可学」，用故意做小的模型去证更有说服力——小模型学会了，说明映射本身简单，排除了靠容量硬记的解释。

## 数据：OCR 70%、通用视觉 20%、纯文本 10%

最终配比是 OCR 数据 70%、通用视觉数据 20%、纯文本数据 10%，序列长度 8192（PDF p. 9）。

### OCR 1.0：文档与自然场景

「OCR 1.0」指传统的文档与场景文字识别（PDF p. 7–8）：

- 从互联网收集 **30M 页 PDF**，覆盖约 100 种语言，中英文约 25M 页、其他语言约 5M 页；
- **粗标注**直接用 `fitz` 从 PDF 抽文字，主要教模型认光学文字，尤其是小语种；
- **细标注**中英文各 2M 页，用 PP-DocLayout 这类版面模型和 MinerU、GOT-OCR2.0 这类 OCR 模型，构造「检测 + 识别」交错的数据；
- 粗标和细标在训练时**用不同的提示词区分**；
- 另有 **3M 份 Word 文档**，直接抽内容做无版面的图文对，主要帮助公式和 HTML 表格；
- 自然场景 OCR 以中英文为主，图来自 LAION 和 Wukong，用 PaddleOCR 打标，中英文各 10M 条，同样用提示词控制是否输出检测框。

细标注的样本长这样。下面几行摘自原文 Figure 5(b)（PDF p. 8），每段文字前面是它的类别和坐标框，**坐标统一归一化到 1000 个格子**：

```text
<|ref|>text<|/ref|><|det|>[[460, 95, 896, 132]]<|/det|>
Prvi dan trčanja Tomislav može izabrati na 7 različitih načina.

<|ref|>equation<|/ref|><|det|>[[460, 217, 550, 256]]<|/det|>
\[ \frac{7 \cdot 4}{2} = 14. \]

<|ref|>table<|/ref|><|det|>[[57, 450, 360, 500]]<|/det|>
<table><tr><td>3</td><td></td><td></td><td></td><td>4</td></tr></table>
```

版面和文字被编进同一条序列，模型学的是「在哪里有什么」。后面「深度解析」要先找到图的位置，靠的就是这套格式。

小语种标注用了一个模型飞轮（PDF p. 8）：版面模型的**检测**能力跨语言泛化得不错，可以直接用；**识别**那一半，先用 `fitz` 造小块图文对训一个 GOT-OCR2.0，再让它去标版面切出来的小块，最终造出 600K 条数据。关键在第一步的观察：拆成检测和识别之后，只有一半真的缺数据。

### OCR 2.0：图表、分子式、几何图

沿用 GOT-OCR2.0 的叫法，「OCR 2.0」指人造图形的结构化解析（PDF p. 8–9）：

- **图表**：用 pyecharts 和 matplotlib 渲染 10M 张折线、柱状、饼图和复合图。标签用 **HTML 表格**而不是 OneChart 的字典格式，理由是更省 token（PDF p. 9，Figure 6）；
- **化学式**：从 PubChem 取 SMILES，用 RDKit 渲染，构造 5M 图文对；
- **平面几何**：按 Slow Perception 的方式生成，perception-ruler 取 4；标签是含线段、端点坐标、线段类型的字典。还做了**平移不变增强**：同一个几何图在画面里平移，标准答案始终画在坐标系中心，共 1M 条。

平移不变增强让模型学的是图形之间的相对结构，而不是线段落在画布的哪个绝对位置。

### 通用视觉与纯文本

- **通用视觉 20%**：按 DeepSeek-VL2 的方式造 caption、检测、grounding 数据。报告强调 DeepSeek-OCR **不是通用 VLM**，这部分只为保留通用视觉接口（PDF p. 9）；
- **纯文本 10%**：内部预训练文本，统一切成 8192 token，用来保住语言能力（PDF p. 9）。

报告**没有 SFT 阶段**，模型不是聊天模型，有些能力要靠补全式提示词才能激活（PDF p. 18，Figure 12 图注）。

## 训练：两段，一半冻结

**第一段，单独训 DeepEncoder**（PDF p. 10）：跟 Vary 一样，接一个紧凑的语言模型（引用的是 OPT-IML，PDF p. 20 参考文献 [15]），用下一个 token 预测来训编码器。数据是全部 OCR 1.0 和 2.0 数据，加上从 LAION 采样的 100M 条通用数据；2 个 epoch，batch 1280，AdamW，余弦退火，学习率 5e-5，序列长度 4096。

**第二段，训完整的 DeepSeek-OCR**（PDF p. 10）：

- HAI-LLM 平台，流水线并行 4 段（分法见上一节）；
- 20 个节点、每节点 8 张 A100-40G，数据并行 40，全局 batch 640；
- AdamW，按步衰减，初始学习率 3e-5；
- 训练速度：纯文本数据每天 90B token，多模态数据每天 70B token。

报告**没有给总训练时长、总 token 数和总成本**，只凭这两个吞吐推不出训练规模。

## 核心实验：压缩率与精度

实验设置（PDF p. 10–11）：

- 用 Fox 基准的英文文档部分，用 DeepSeek-OCR 自己的分词器（词表约 129k）切标准答案；
- 选 600–1300 个 text token 的文档，正好 100 页；
- 文字量不大，只测 Tiny（64 token）和 Small（100 token）两档；
- 提示词用不带版面的 `<image>\nFree OCR.`。

Table 2（PDF p. 10）：

| 文本 token 区间 | 64 token 精度 | 64 token 压缩率 | 100 token 精度 | 100 token 压缩率 | 页数 |
|---|---:|---:|---:|---:|---:|
| 600–700 | 96.5% | 10.5× | 98.5% | 6.7× | 7 |
| 700–800 | 93.8% | 11.8× | 97.3% | 7.5× | 28 |
| 800–900 | 83.8% | 13.2× | 96.8% | 8.5× | 28 |
| 900–1000 | 85.9% | 15.1× | 96.8% | 9.7× | 14 |
| 1000–1100 | 79.3% | 16.5× | 91.5% | 10.6× | 11 |
| 1100–1200 | 76.4% | 17.7× | 89.8% | 11.3× | 8 |
| 1200–1300 | 59.1% | 19.7× | 87.1% | 12.6× | 4 |

报告的读法：10× 以内精度约 97%，超过 10× 开始下降，接近 20× 仍接近 60%（PDF p. 11–12）。它还提醒，模型输出格式和 Fox 的标准答案不能完全对齐，**真实性能会比测出来的略高**（PDF p. 11）。据此报告展望「未来或许」能通过文字转图像实现接近 10× 的近乎无损压缩（PDF p. 11）——这是展望，原文用的是 may be possible。

封面的 Figure 1(a) 画的是同一组数，但有两格与 Table 2 差 0.1：图上是 85.8% 和 76.3%，表里是 85.9% 和 76.4%（PDF p. 1、p. 10）。以正文表为准。

### 这张表不该怎么读

![Table 2 的 14 个点画在压缩率—精度平面上：100 个 token 那组都在 13× 以内且精度 87% 以上，64 个 token 那组从 10.5× 一路降到 19.7× 的 59.1%；压缩率都约 10.5× 的两点精度差 5 个百分点。](/reports/DeepSeek-OCR/figure-compression-precision.svg)

下面几条是我们的解读，结论都建立在 Table 2 上：

1. **压缩率是被观测的量，不是被拧的旋钮。** 每一列里 vision token 数是固定的，变的是分子——这页有多少字。Figure 1(a) 的横轴正是「每页标准答案的 text token 数」，压缩率画在副轴上（PDF p. 1）。所以精度下降的直接原因是文档变密了。
2. **同样的压缩率，精度可以不同。** 64 token、600–700 字是 10.5×、96.5%；100 token、1000–1100 字是 10.6×、91.5%。压缩率几乎一样，精度差 5 个点。文档的绝对长度和版面复杂度是压缩率之外的独立变量，「10× 近乎无损」要带上「Fox 英文单页、这种版面」的限定。
3. **最常被引用的那一档样本最少。** 19.7×、59.1% 那一行只有 4 页。
4. **曲线有噪声。** 64 token 那组 800–900 字是 83.8%，900–1000 字反而升到 85.9%。它是趋势，不是可以外推的函数。
5. **「precision」的算法报告没有定义。** 它可能是按字符编辑距离换算的，也可能不是；只知道是 OCR 解码精度。

### 报告给的两个下降原因，与一次「缺陷变特性」

超过 10× 为什么掉，报告给了两个猜测（PDF p. 11–12）：

1. 长文档的版面更复杂——报告说这可以通过把文字渲染到统一版面的单页上来解决；
2. 在 512×512 或 640×640 下，长文本会变糊——报告说「我们相信第二个问题会成为遗忘机制的一个特性」。

同一个现象，在 OCR 语境里是失败，在「模拟记忆衰减」的语境里被重新定义成特性。这个重新定义**没有实验支撑**，后文讨论遗忘机制时会再看。

报告还说，这套方法「不带来任何额外开销」，因为多模态系统本来就有视觉编码器（PDF p. 12）。这句话只对已经是多模态的系统成立；对纯文本模型，为压上下文挂一个视觉编码器是实打实的新增成本。

## 换到真实文档：更少的 token 能走多远

OmniDocBench 是真实文档解析基准，指标是**编辑距离，越小越好**。Table 3 摘录（PDF p. 11）：

| 模型 | 平均 vision token | 英文 overall | 中文 overall |
|---|---:|---:|---:|
| GOT-OCR2.0 | 256 | 0.287 | 0.411 |
| Qwen2.5-VL-72B | 3949 | 0.214 | 0.261 |
| InternVL3-78B | 6790 | 0.218 | 0.296 |
| Gemini2.5-Pro | — | 0.148 | 0.212 |
| MinerU2.0 | 6790 | 0.133 | 0.238 |
| dots.ocr（200dpi） | 5545 | 0.125 | 0.160 |
| DeepSeek-OCR Tiny | 64 | 0.386 | 0.361 |
| DeepSeek-OCR Small | 100 | 0.221 | 0.284 |
| DeepSeek-OCR Base | 256（有效 182） | 0.137 | 0.240 |
| DeepSeek-OCR Large | 400（有效 285） | 0.138 | 0.208 |
| DeepSeek-OCR Gundam | 795 | 0.127 | 0.181 |
| DeepSeek-OCR Gundam-M（200dpi） | 1853 | **0.123** | **0.157** |

报告自己挑出的三条对照（PDF p. 12）：

1. **100 个 token**（640×640）就超过用 256 个的 GOT-OCR2.0：英文 0.221 对 0.287；
2. **400 个 token（有效 285）** 与该基准上的最好成绩「持平」：Large 英文 0.138，表中别家最好的是 dots.ocr（200dpi）的 0.125、MinerU2.0 的 0.133，「持平」是报告的措辞；
3. **不到 800 个 token 的 Gundam** 超过要近 7000 个 token 的 MinerU2.0：英文 0.127 对 0.133，中文 0.181 对 0.238。

第三条最能说明问题：token 预算差 8 倍以上，成绩还略好。摘要里对 MinerU2.0 写的是「平均每页 6000 以上」，正文写「近 7000」，表里是 6790（PDF p. 1、p. 11–12）。

两处非单调，报告没有点出来：

- **Base 到 Large，英文没有进步**：0.137 → 0.138，中文却从 0.240 降到 0.208。一种合理的推测是英文在 Base 分辨率下已基本看清，中文笔画更密，还能吃到分辨率红利（本文推测）。
- **Table 4 有一格异常**：Gundam 在财报类上是 0.289，而 Base 是 0.027、Large 是 0.022、Gundam-M 是 0.034（PDF p. 12）。只有这一格高出一个数量级，报告没有解释，无法判断是真实退化还是录入错误。

## 不同版面需要的 token 数差了一个数量级

| 模式 | 书 | 幻灯片 | 财报 | 教材 | 试卷 | 杂志 | 学术论文 | 笔记 | 报纸 | 总体 |
|---|---:|---:|---:|---:|---:|---:|---:|---:|---:|---:|
| Tiny（64） | 0.147 | 0.116 | 0.207 | 0.173 | 0.294 | 0.201 | 0.395 | 0.297 | 0.940 | 0.320 |
| Small（100） | 0.085 | 0.111 | 0.079 | 0.147 | 0.171 | 0.107 | 0.131 | 0.187 | 0.744 | 0.205 |
| Base（256） | 0.037 | 0.080 | 0.027 | 0.100 | 0.130 | 0.073 | 0.052 | 0.176 | 0.645 | 0.156 |
| Large（400） | 0.038 | 0.108 | 0.022 | 0.084 | 0.109 | 0.060 | 0.053 | 0.155 | 0.353 | 0.117 |
| Gundam（795） | 0.035 | 0.085 | 0.289 | 0.095 | 0.094 | 0.059 | 0.039 | 0.153 | 0.122 | 0.083 |
| Gundam-M（1853） | 0.052 | 0.090 | 0.034 | 0.091 | 0.079 | 0.079 | 0.048 | 0.100 | 0.099 | 0.077 |

报告的读法（PDF p. 12）：幻灯片 64 个 token 就够；书和报告 100 个就不错；报纸必须上 Gundam 甚至 Gundam-master，因为报纸一页有 4000–5000 个 text token，远超其他档 10× 的压缩能力。报纸那一列从 Tiny 的 0.940（几乎全错）降到 Gundam-M 的 0.099。

报告把原因接回了上一节：这些类别少 token 就够，是因为多数页面文字在 1000 token 以内，压缩率没超过 10×（PDF p. 12）。于是因果链闭合：**文档类型决定文字密度，文字密度决定压缩率，压缩率决定精度。**

注意两处与总表的口径差异：Table 4 的「总体」一行（如 Small 0.205、Base 0.156）与 Table 3 的英文、中文 overall 都不相同，报告没有说明 Table 4 的总体是怎么合并的。另外表中把 Gundam-M 拼成了「Guandam-M」（PDF p. 12）。

**可迁移启发**：按量计费的多模态服务，先看输入的类型分布，再决定档位。幻灯片给 64，报纸给上千，平均成本可能降一个数量级。

## 深度解析：OCR 之外多一层结构

![原文 Figure 7：金融研报页面先用 grounding 提示词转成带版面框的 Markdown，再对其中一张柱状图用「Parse the figure.」二次调用，输出与柱高对应的数据表。](/reports/DeepSeek-OCR/figure7-deep-parsing.png)

原文 Figure 7（PDF p. 13）。报告把这项能力叫 deep parsing（深度解析）：先把整页转成带版面的 Markdown，再对页面里的图做**二次模型调用**，用统一提示词 `<image>\nParse the figure.` 解析（PDF p. 12）。四个演示分别是（PDF p. 13–16）：

- 研报里的图表 → 数据表（Figure 7）；
- 书里的自然图片 → 密集描述（Figure 8）；
- 化学文档里的分子式 → SMILES（Figure 9）；
- 简单几何图 → 线段结构（Figure 10）。报告自己说几何解析「还有很长的路要走」。

多语言方面覆盖近 100 种语言，同样可以按提示词输出带版面或不带版面的结果，演示用的是阿拉伯语和僧伽罗语（PDF p. 16–17）。通用视觉保留了描述、检测、指代定位等能力（PDF p. 17–18）。

从压缩主线看，深度解析说明视觉 token 里保留的**不只是字形，还有结构**：一张图表压成 token 之后，还能恢复出数值和表格。但这些都是定性演示，**报告没有给深度解析的任何定量指标**。

### 提示词就是接口

把报告里出现过的提示词拼起来（PDF p. 11、p. 13–18）：

| 提示词 | 输出 |
|---|---|
| `<image>\nFree OCR.` | 纯文本，不带版面 |
| `<image>\n<\|grounding\|>Convert the document to markdown.` | 带版面框的 Markdown |
| `<image>\nParse the figure.` | 图内元素的结构化解析 |
| `<image>\nLocate <\|ref\|>the teacher<\|/ref\|> in the image.` | 指定对象的定位框 |
| `<image>\nIdentify all objects in the image and output them in bounding boxes.` | 全图检测 |
| `<image>\nDescribe this image in detail.` | 密集描述 |
| `<image>\n这是一张` | 补全式续写 |

这些开关之所以有效，是因为**训练数据里就用不同提示词区分了不同标注**：粗标与细标、场景 OCR 要不要框、小语种带不带版面（PDF p. 8、p. 16）。它们是模型学过的分支，不是训练后临时凑出来的提示词工程。最后那条没写完的中文句子，也印证了模型没有做 SFT、要靠补全来激活（PDF p. 18）。

## 它还是一台数据生产机

两组产能数字（PDF p. 1、p. 3）：

- 单张 A100-40G，每天 20 万页以上；
- 20 个节点、每节点 8 张 A100-40G，每天 3300 万页。

两者自洽：$200{,}000 \times 160 = 3.2 \times 10^7$，与 3300 万同一量级（本文核算）。这 20 个节点也正是训练用的那套集群配置（PDF p. 10）。

但这组数字**没有说明用的是哪一档分辨率**。Tiny 的 64 个 token 和 Gundam-master 的上千个 token 计算量差很多；而按 Table 4，低档在报纸上几乎不可用。产能没有和质量绑定，不能直接换算成「一天能产多少可用数据」（本文判断）。

## 最大胆的一段：把遗忘写进上下文

Discussion 一节（PDF p. 18–19）是全篇最有想象力、也最需要小心读的部分。

报告的提议是：多轮对话里，把**超过 $k$ 轮之前**的历史渲染成图，得到约 10× 的压缩（PDF p. 18）；**越久远的上下文，图就缩得越小**，token 消耗继续下降（PDF p. 19）。

Figure 13 用三行并列的类比表达这个想法（PDF p. 19），改写成表：

| 清晰度 | Crystal Clear | Very Clear | Clear | Blurry | Very Blurry | Almost Gone |
|---|---|---|---|---|---|---|
| 记忆（时间 →） | 刚发生 | 1 小时 | 1 天 | 1 周 | 1 个月 | 1 年 |
| 视觉（距离 ↑） | 10cm | 50cm | 1m | 3m | 10m | 20m |
| 文本（分辨率 ↓） | 文本 token | Gundam | Large | Base | Small | Tiny |

报告的说法是：人类记忆随时间衰减，与视觉随距离退化呈现相似的渐进信息损失；光学压缩可以模拟这种「近清远糊」的遗忘曲线，并「指向一条理论上无限上下文的路径」（PDF p. 19）。

这个类比指向一个真问题，但证据等级必须分清：

- **已经证明的**：静态单页英文文档上，约 10× 压缩时 OCR 精度约 97%，约 20× 时约 60%。
- **只是提议的**：把对话历史渲染成图、按年龄分级降分辨率、由此得到无限上下文。
- **报告自己承认还没做的**：数字—光学文本交错预训练、大海捞针测试（PDF p. 19）。

后两项恰恰是验证这个提议最关键的实验。OCR 测的是**逐字还原**；长上下文需要的是**按问题检索**。一个能把整页背出来的模型，未必能回答「第三段提到的数字是多少」。报告把大海捞针列为未来工作，说明作者清楚这个缺口，也明说这是需要进一步研究的早期工作（PDF p. 19）。

## 报告没有回答的问题

**方法**

- 没有 DeepEncoder 的结构消融；
- 没有和文本侧压缩方法（摘要、token 剪枝、KV Cache 量化）在同等预算下对比，所以「光学压缩更优」没有被证明，被证明的只是「可行」；
- 没有量化渲染参数（字号、行距、dpi、排版）对压缩率的影响，而这正是「把上下文渲染成图」的核心自由度。

**评测**

- 压缩率曲线只有英文（PDF p. 10），中文等语种没有数据；
- 最高那一档只有 4 页；
- 「precision」没有定义；
- 深度解析没有定量指标；没有大海捞针。

**系统**

- 没有显存、延迟、吞吐的对比实测；
- 没有总训练时长、总 token 数与成本；
- 没有说明视觉 token 与文本 token 在同一序列里交错时怎么处理位置编码——这是未来交错预训练的前提。

**能力**

- 没有 SFT，不是聊天模型（PDF p. 18）；
- 数据的过滤、去重、质量模型没有公开。

## 能带走的六条设计原则

1. **把直觉逼成一个可测的比值。** 「一图胜千言」一直是修辞；写成 $N_{\text{text}} / N_{\text{vision}}$ 之后，它才能被测量和优化。
2. **昂贵模块前面放降采样。** 平方复杂度的那一段，先让它的输入变短，再谈常数优化。
3. **把实验自变量做成模型的输入条件。** 多分辨率模式让一份权重扫出整条曲线，省算力，也省掉跨模型对比的混淆。
4. **证明可学性，用故意做小的模型。** 下界比上界更有信息量。
5. **有损压缩可以设计成分级保真，但要配新目标下的实验。** 把缺陷重新定义为特性，没有实验就只是话术。
6. **按输入类型分档。** 同一个模型，幻灯片和报纸需要的 token 预算差一个数量级。

## 关键词回看

- **上下文光学压缩**：把文字渲染成图，用视觉 token 承载，缩短序列。
- **压缩率**：标准答案 text token 数 ÷ 视觉 token 数；本报告里是被观测的量，不是被调的旋钮。
- **DeepEncoder**：SAM-base（窗口注意力，冻结）+ 16× 卷积压缩 + CLIP-large（全局注意力，可训），约 380M。
- **视觉分词器 / 输入嵌入层**：报告在流水线切分时对前后两半的称呼。
- **原生分辨率 / 动态分辨率**：Tiny、Small、Base、Large 四个固定尺寸；Gundam 系列由局部瓦片加全局视图组成。
- **有效视觉 token**：补边模式下扣掉空白后真正带信息的 token 数，按式 1 折算。
- **OCR 1.0 / OCR 2.0**：前者是文档与场景文字识别；后者是图表、化学式、几何图的结构化解析。
- **模型飞轮**：先用简单方法造数据训小模型，再用小模型标更难的数据。
- **深度解析**：整页转 Markdown 之后，再对页内图片做二次解析。
- **遗忘机制**：Discussion 中的设想，越久远的上下文用越低的分辨率保存。它是提议，不是已实现的机制。
- **编辑距离**：OmniDocBench 的指标，越小越好。

## 最后的判断

这份报告的标题写着 OCR，真正问的是：**文本 Token 是不是承载文本的唯一合理载体？**

它的答案边界清楚。**已经成立的**：单页英文文档上，约 10× 压缩时 OCR 精度约 97%、约 20× 时约 60%；一个 380M 的编码器加 570M 激活参数的解码器就能做到；在真实文档解析上，用不到 800 个 token 就超过需要 6790 个 token 的专用工具。这些有表、有基准、有样本量。

**还只是提议的**：把对话历史渲染成图、按年龄分级降分辨率、从而得到近乎无限的上下文。这一段没有实验，报告自列的两项关键验证都没做。

所以最恰当的读法是：**一次成功的可行性测量，加一个尚未验证的架构设想。** 它最有价值的不是 DeepEncoder 这个具体结构（结构消融一个都没有），而是把一个停留在比喻层面的想法，变成了一条能画出来、能看出拐点、能标出样本量的曲线。

如果只带走一句：

> **当一种表示的代价随规模超线性增长时，值得认真考虑换一种模态来承载同样的信息；换了之后损失可控，而且损失程度可以做成一个连续的旋钮——旋钮存在已被证明，旋钮怎么用还没有。**

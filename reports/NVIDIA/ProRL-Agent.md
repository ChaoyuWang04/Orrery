# ProRL Agent：把多轮 Agent 的 rollout 从训练进程里搬出来，做成一个 HTTP 服务

<!-- release-date: 2026-03-19 -->

> 本文依据 **ProRL Agent: Rollout-as-a-Service for RL Training of Multi-Turn LLM Agents**，arXiv:2603.18815v1，2026-03-19 提交，共 22 页（正文与结论 p. 1–14，参考文献 p. 15–17，附录 A 的六张进程放置图 p. 18–22）。十三位作者，Hao Zhang、Mingjie Liu、Shaokun Zhang 三人标为核心贡献者；首页没有逐人标注单位，页脚是「© 2026 NVIDIA」（PDF p. 1）。页码均指 PDF 自身的页码。文中区分三件事：**论文明确写了什么**、**我们怎么解释它**、**哪些是外部资料**。只在图上出现的数字会注明读自哪张图。

## 读前先把几个词说成人话

- **多轮 Agent 与 rollout**：给模型一个任务，比如「修好这个仓库里的 bug」。模型写一个动作（一条 shell 命令、一次文件编辑），动作在隔离环境里执行，结果追加回上下文，模型再写下一个动作，往复几十次。这一整串「动作 → 观察」叫一条**轨迹（trajectory）**，把它跑出来的过程叫 **rollout**。论文说这类轨迹常常跨几十个回合、几万个 token（PDF p. 1）。
- **RLVR（Reinforcement Learning from Verifiable Rewards，可验证奖励强化学习）**：让当前模型跑一批轨迹，用规则打分（代码任务跑测试，数学题比对答案），再按分数更新模型。算法侧见 DeepSeekMath、DAPO 两篇。
- **训练器（trainer）**：负责算优势、反向传播、更新权重的那部分程序，比如 veRL、NeMo RL。
- **推理引擎**：vLLM、SGLang 这类专门负责生成的服务。rollout 里每一步模型「想下一步」都要调它一次。
- **沙箱（sandbox）与脚手架（scaffold）**：沙箱是让 Agent 跑命令、改文件的隔离环境，通常是一个容器；脚手架是包在模型外面、组织提示词、解析动作、调工具的那层代码，OpenHands、SWE-agent 都是。
- **Docker、Singularity 与 Slurm**：前两者是容器技术。Docker 需要一个常驻、近似 root 权限的守护进程；Singularity 不需要守护进程、以普通用户身份运行。Slurm 是高性能计算（HPC）集群上最常见的作业调度器，用户通常没有 root，也不能随便起常驻服务（PDF p. 4、p. 6）。

## 一句话先说清

多轮 Agent 的 RL 训练里，「跑 Agent」和「训模型」是两种完全不同的活。前者要建沙箱、维持长时间的工具会话、同时协调几百个实例，是 I/O 密集的；后者是前向、反向、梯度同步，是 GPU 密集的（PDF p. 1–2）。

![Figure 1 左右两栏对比：(a) 耦合设计里，沙箱管理、工具执行、评估与奖励组成的 Rollout Loop 画在 RL Training Loop 的大框之内，与策略更新和推理引擎挤在一起；(b) 解耦设计里，一条标着 HTTP 的红色虚线把上方只剩策略更新的训练循环和下方的 ProRL Agent（Rollout Server）隔开，训练侧发 Rollout Request、收回奖励与轨迹，rollout 服务另经 REST API 调推理引擎。](/reports/ProRL-Agent/fig1-coupled-vs-decoupled.png)

左边是论文眼里的现状，右边是它的答案（PDF p. 2，Figure 1）。现有框架把 Agent 的整个 rollout 生命周期写在训练器里，这带来两笔账（PDF p. 1–2）：

1. **资源需求冲突。** 两种负载放在一起互相干扰，整体资源效率下降。
2. **难迁移、难维护。** 换一个训练后端，往往要把整条 Agent 执行流水线重写一遍；给 rollout 加一种新环境、新任务，改动又会波及训练代码。

论文借了推理引擎的思路：vLLM、SGLang 把「推理」做成谁都能调的服务，那就把「rollout」也做成服务，称为 **rollout 即服务（rollout-as-a-service）**（PDF p. 2）：

> ProRL Agent 是一个独立的 HTTP 服务。训练器提交一个任务实例，服务在内部跑完从建环境到评分的整条轨迹，把带奖励的轨迹交回去；训练器不管理 rollout 生命周期的任何一部分。（PDF p. 2）

为了让它在真实集群上跑得动，论文另做了三件事：训练链路全程传 token id、不传文本；任务写成可插拔的沙箱环境；免 root 部署，能在共享的 Slurm 集群上跑几百个并发 rollout（PDF p. 2）。

验证结果：用 DAPO 在 32 张 H100 上训练，SWE-Bench Verified 上 Qwen3 的 4B、8B、14B 分别从 14.8 到 21.2、9.6 到 18.0、15.4 到 23.6（PDF p. 11，Table 2）。**要先记住一点：全文没有任何「比别的框架快多少」的对照实验。** 它证明的是这套东西能把 RL 训起来、能扩展；消融只在自己内部做（PDF p. 13）。

## 主要矛盾：rollout 写在训练进程里

正文用一张勾叉表概括现状（PDF p. 3，Table 1）：

| 框架 | 训练与 rollout 解耦 | 免 root 沙箱 | 不绑定脚手架 |
|---|:---:|:---:|:---:|
| SkyRL-Agent | ✗ | ✗ | ✓ |
| VeRL-Tool | ✗ | ✗ | ✓ |
| Agent Lightning | ✗ | ✗ | ✗ |
| rLLM | ✗ | ✗ | ✓ |
| GEM | ✗ | ✗ | ✓ |
| ProRL Agent | ✓ | ✓ | ✓ |

表头第三列写的是 Scaffold-Independent，表注却说 ProRL Agent「独立于任何具体的训练框架」（PDF p. 3），两者不是一回事。第 3.1 节对「脚手架可替换」的说法是：脚手架可以修改或替换，而不影响训练基础设施（PDF p. 5）。

「✗」到底什么意思，要看附录的进程放置图（PDF p. 19–22）。归纳下来是三种形状：

| 形状 | 谁 | 附录图里的证据 |
|---|---|---|
| 推理与环境都外包，Agent 循环还在训练驱动里 | SkyRL-Agent | 训练驱动进程里跑 512 个协程（64 条 prompt × 8 条轨迹），每个协程自己走 50 轮循环，经 Ray RPC 调远端 vLLM、经 HTTP 调远端 Docker（PDF p. 19，Figure 7） |
| 只把工具执行外包 | VeRL-Tool | 训练器里的 `AgentLoopWorker` 做生成、解析、调工具、追加观察；工具服务器在 CPU 节点，按 CRC32 做粘性路由到 8 个后端 worker（PDF p. 21，Figure 9） |
| 全部在一棵进程树里 | Agent Lightning、rLLM、GEM | Agent Lightning 的 `LightningStoreServer` 是训练进程里的后台线程，rollout runner 由训练器派生，训练进程一退出 store 就停（PDF p. 20，Figure 8）；rLLM 在单个驱动进程里用线程池建 Docker 环境、跑 Agent、算奖励（PDF p. 21，Figure 10）；GEM 把 16 个环境当内存里的 Python 对象直接 `env.step()`（PDF p. 22，Figure 11） |

三种形状的共同点是：**rollout 何时开始、跑到哪一步、何时结束，都由训练进程的代码决定。** 论文由此判断，换训练后端往往要把整个 rollout 栈重写或移植，这层摩擦常常比训练算法本身更耗工程精力（PDF p. 3）。

沙箱这一侧还有第二个耦合。R2E-Gym、SWE-bench、OpenHands、SWE-agent 这些现有平台深度依赖 Docker；Docker 假设有守护进程和近似 root 的权限，共享的 Slurm 集群通常两样都不给。实践者要么为评测和部署各维护一套基础设施，要么承担在受限系统上跑特权容器的运维负担（PDF p. 4）。**沙箱起不来，前面的解耦就无从谈起**，这是全文「免 root」一线的来历。

## 先看全景：三层，一条 HTTP 边界

![Figure 2 是三层架构：最上层 ③ RL trainer 含「任意训练器（veRL、NeMo RL）」「Efficient DAPO」「LLM 服务器负载分配」三块；一条标 ProRL Agent 的虚线之下是 ② ProRL Agent Server，含异步流水线 INIT、RUN、EVAL，LLM 后端池（min-heap、动态注册），HTTP 接口；最下层 ① Sandbox Environment 含 Singularity Runtime（fakeroot、每容器回环 IP）与 AgentHandler（init、run、eval）。训练器经 POST /process、/add_llm_server、/cancel 向下，服务把轨迹与奖励交回。](/reports/ProRL-Agent/fig2-architecture.png)

三层各管一件事（PDF p. 4，Figure 2）：

- **沙箱环境**：每条 rollout 在一个 Singularity 容器里执行，由 `AgentHandler` 的 `init`、`run`、`eval` 三个生命周期方法驱动；
- **ProRL Agent Server**：用三个独立的工作池管理几百条并发 rollout，并维护一个 LLM 后端池；
- **训练器**：只通过 HTTP 与服务交互，提交任务、管理后端、收回轨迹与奖励。

论文说这条边界带来三个实际后果（PDF p. 4–5）：训练器和 rollout 逻辑可以分别开发、分别部署，rollout 节点和训练节点分开调优；加一个新任务只需在服务端写一个 handler 插件，训练代码不改；脚手架可以换，训练基础设施不受影响。

**有一条边界容易漏看：推理引擎不在服务里，权重更新也不归服务管。** 推理引擎由训练侧部署，训练器把地址注册给服务；更新完策略，是训练器自己把新权重装进推理引擎，再通知服务换后端（PDF p. 8）。所以 ProRL Agent 解耦的是「Agent 执行」与训练，不是「生成」与训练。这决定了它和 AReaL、Laminar 那类异步 RL 系统不在同一个问题上，后文再说。

### 一条任务的一生

![Figure 6 是一张进程放置示例：左边是 4 个 GPU 节点、每节点 8 卡的训练集群，驱动进程依次准备一批任务实例、POST /process、按任务收回 HTTP 响应，再张量化、计算优势、更新 actor；右边是 CPU 或 GPU 节点上的 start_server.py 起的 FastAPI 服务，列出管理端点，下面的 OpenHandsServer 跑 INIT、RUN、EVAL 三段，RUN 段是 50 轮的 Agent 循环（token id 发给 vLLM、收回回复与对数概率、动作发给 Singularity 环境、收回观察），EVAL 段是应用 git patch、跑测试、算奖励。](/reports/ProRL-Agent/fig6-process-placement.png)

以软件工程任务为例，按附录 Figure 6 与正文 Listing 2、Listing 3 走一遍（PDF p. 7–9、p. 18）：

1. **提交。** 训练器准备一批任务实例，逐个发 `POST /process`，请求体是任务实例和采样参数。服务把任务放进 INIT 队列，HTTP 处理器挂起等待这个任务的完成事件。
2. **建环境。** INIT 池的 worker 在注册表里找到任务对应的 handler，调 `init`：起一个 Singularity 容器、分配回环 IP、装好工具，任务进 RUN 队列（PDF p. 5–6）。
3. **跑 Agent。** RUN 池的 worker 调 `run`。它先从后端池挑一个推理后端并固定给这个任务（PDF p. 9），然后进入最多 50 轮的循环：把上下文的 token id 发给 vLLM，收回回复的 token id 与逐 token 对数概率；解析出动作，经 Unix domain socket 发给容器内的执行服务器，拿回观察（PDF p. 6–7、p. 18）。循环结束先释放容器，任务进 EVAL 队列（PDF p. 8）。
4. **评分。** EVAL 池的 worker 调 `eval`：应用 git patch、跑测试、算奖励（PDF p. 18）；结果序列化后置完成事件，唤醒第 1 步挂起的 HTTP 处理器，轨迹与奖励作为响应返回（PDF p. 8）。
5. **训练。** 训练器收齐一批，张量化、算优势、更新 actor，把新权重装进推理引擎，然后先 `/clear_llm_server` 再逐个 `/add_llm_server`（PDF p. 8、p. 18）。
6. **出岔子。** 任何一段抛异常，对应的异常回调填一个结构化的兜底结果并照样置完成事件（PDF p. 9）；训练器把出错的 rollout 排除在梯度之外（PDF p. 11）；攒够有效样本后，对剩下的任务发 `/cancel`（PDF p. 9）。

训练器只出现在第 1、5、6 步，每次都只是一个 HTTP 请求。**这就是「rollout 即服务」的全部含义：训练器知道任务何时交出、何时回来，不知道中间发生了什么。**

「最多 50 轮」只出现在这张示例图里，正文没有给实验用的轮数上限。图里服务核心的名字叫 `OpenHandsServer`，消融里「去掉 Efficient Bash」的对照是 OpenHands 原版实现（PDF p. 13、p. 18），可以推断软件工程任务用的是 OpenHands 的脚手架；正文没有直说。

## 核心设计一：把任务写成三段式插件

**旧问题。** 软件工程、数学推理、电脑操作，各有各的环境准备、Agent 行为和奖励算法。把这些差异硬编码进服务器，服务器会变脆，而且永远离不开大量人工（PDF p. 5）。

**新设计。** 任务相关的逻辑全部封进抽象接口 `AgentHandler`，三个方法对应流水线三段（PDF p. 5，Listing 1）：

- `init`：为任务初始化沙箱，配好工具集，返回运行时、元数据和配置；
- `run`：在沙箱里驱动多轮 Agent 循环，收集「动作—观察」轨迹和任务产物；
- `eval`：把 Agent 的输出和标准答案比对，返回一个标量奖励。

每个 handler 还要提供三个按阶段的异常回调和一个负责序列化的 `final_result`，保证 rollout 中途失败时服务也总能吐出格式良好的结果（PDF p. 5）。任务域各自继承 `AgentHandler`、按唯一名字注册，服务收到任务后查表分派（PDF p. 5–6）。

**为什么是三段，而不是一个 `run()`。** 这不是为了代码整洁。只有把 I/O 受限的准备、推理受限的执行、时长不定的评估切开，它们才能被分到三个独立的工作池里并行推进（PDF p. 7–8）。

**收益。** 第 4 节的四个任务域，就是四个 handler 加各自的工具配置和奖励设计（PDF p. 11–12）。

**代价与边界。** 每个任务都得有人写 handler，而 `run()` 里那个多轮循环就是脚手架本身。也就是说，Agent 逻辑仍要以「实现一个 handler」的形式搬进服务。这正是后作 Polar 改掉的那一点（见后文「与后作 Polar 的分工」）。

**可迁移启发。** 给一个长流程定接口时，先按**资源类型**切段，再谈业务含义。瓶颈不同才是能并行的前提；异常回调按段配置，「哪一段坏了」才会变成一条结构化信息，而不是一个未捕获的异常。

## 核心设计二：三条队列、三个工作池

![按阶段分池的机制示意：上半「一个 worker 包到底」，三个 worker 各自顺序做完 INIT、RUN、EVAL，开头大家都在起容器、中段大家都在打分或起容器时，出现两段灰带表示没有任何任务在 RUN、推理后端没活干；下半「三条队列、三个池」，INIT 池提前备好容器，RUN 池的三个槽位从第一个任务之后一直是满的，J1 的长测试只占 EVAL 池的一个槽位。](/reports/ProRL-Agent/three-stage-pipeline.svg)

**旧问题。** 论文用装配线打比方（PDF p. 8）：朴素做法是一个 worker 包一个任务，起容器、跑 Agent、打分全做完再接下一个。三段的耗时和资源完全不同：起容器在等磁盘和网络；Agent 每次调用快，但要发几十次 LLM 请求，瓶颈是 GPU；评估可能瞬间完成（比对一个数学答案），也可能跑好几分钟（整套测试）。一个 worker 顺序坐完三段，大部分时间都在等当下最慢的那一段。服务的第一条需求因此写成：三段在每个任务内部执行，但吞吐不应被最慢的一段限制（PDF p. 7）。

**新设计与工作机制。** Listing 2 只有二十来行，每一行换来一条保证（PDF p. 7–8）：

| Listing 2 里的那一行 | 它买到什么 |
|---|---|
| 每个阶段一个线程安全的 FIFO 队列、一个 `ThreadPool(N[s])` | 三段按各自负载分别设并发度：init 多开几个吸收慢启动，测试套件长就多开 eval |
| 取到任务先查 `discarded` 集合，命中就跳过 | 取消是打标记，不用去队列里删元素 |
| `job.timer.phase(stage)` 只包住 handler 调用 | 排队时间不计入超时 |
| 异常时改调 `handler[stage + '_exception']` | 单个任务失败不会弄死 worker 线程，也不会卡住池 |
| RUN 结束先 `cleanup(job.runtime)` | 容器只活到 Agent 循环结束，评估期间不占它 |
| 最后一段 `job.done.set()` | HTTP 处理器等一个事件即可，不必轮询 |

**我们如何解释它。** RUN 一结束就释放容器，那 EVAL 靠什么跑测试？软件工程任务的评估是「应用 git patch、跑测试」（PDF p. 18），而 `run` 会收集「任务产物」（PDF p. 5）。两者放在一起，合理的读法是：patch 作为产物被带出容器，评估在自己的环境里重放。好处是 Agent 干活的容器不必活到评估结束；代价是评估环境要能独立重建。对有标准镜像的 SWE 类任务这是现成的，对状态更复杂的任务（如 GUI 操作）未必。

**收益。** 论文没有单独消融流水线本身。消融里最接近的是「去掉陈旧任务清理、等所有任务都跑完」：吞吐从 0.37 降到 0.30 实例/秒（PDF p. 13，Table 3）。它测的是「等最慢的那个」这件事的代价，和流水线要消除的是同一类等待。

**代价与边界。** 队列是纯 FIFO，没有优先级；三个池的大小要人调，论文没有给任何设置值或自动调整机制；评估失败时 Agent 的中间状态已经随容器销毁，没法回到现场看。

**可迁移启发。** 当一个作业由几段资源类型不同的子任务组成时，按阶段分 worker，不按作业分。判据是某一段的耗时方差是否很大：这里评估从毫秒到数分钟，按作业分 worker 会让整条流水线被这一段的最慢样本拖住，按阶段分只让这一段自己排队。

## 核心设计三：LLM 后端池，按任务粘住同一台

**旧问题。** Agent 循环的每一步都要一次 LLM 补全。几百条 rollout 并行时，请求同时、高频地打到推理层，单台 LLM 服务器很快成为瓶颈，所以要部署一池（PDF p. 8）。服务的第二条需求是：训练器要能动态控制这个池，集群扩容时注册新服务器，checkpoint 更新时换后端，梯度批次已经推进时取消陈旧的在途任务，而且不耦合到服务内部（PDF p. 7）。

**新设计：六个端点。**（PDF p. 8，Listing 3）

| 端点 | 作用 |
|---|---|
| `POST /add_llm_server` | 注册一个推理后端，请求体是地址 |
| `POST /clear_llm_server` | 清空全部后端 |
| `POST /process` | 提交一个任务，请求体是任务实例与采样参数 |
| `POST /cancel` | 中止一个在跑的任务 |
| `POST /start`、`POST /stop` | 服务生命周期 |
| `GET /status` | 各队列深度 |

**checkpoint 交换。** 训练器更新策略后，旧权重失效。它不重启 rollout 服务，而是先 `/clear_llm_server`，再把重新加载过的推理服务地址逐个注册回来；此后所有新 rollout 自动用新模型，已在流水线里的任务不受打断（PDF p. 8）。

**min-heap 负载均衡。** 每个后端带一个分配计数放在最小堆里。RUN 阶段要发 LLM 调用时，服务选计数最小的后端，把**整个任务**分给它（PDF p. 9）：

$$
s^{*}=\arg\min_{s} w_s,\qquad w_{s^{*}}\leftarrow w_{s^{*}}+1
$$

$w_s$ 是后端 $s$ 自注册以来被分配的次数。计数按任务加一，不按调用加一，于是同一任务后续所有调用都落在同一个后端上，最大化前缀缓存复用（PDF p. 9）。拿到流量多的后端自然排到后面，得到类似轮询的均衡，不需要全局同步，整个操作一把锁保护（PDF p. 9）。

**我们如何解释它：为什么按任务而不按调用。** 多轮轨迹的每一步都以前面所有回合为前缀。第 $k$ 步和第 $k+1$ 步落在不同服务器上，第 $k+1$ 步的前缀在那台机器上是冷的，要重新 prefill 几万个 token；落在同一台，前缀的 KV Cache 大概率还热着。附录里 VeRL-Tool 的工具服务器用 CRC32 做粘性会话（PDF p. 21），解决的是同一个问题在工具侧的版本。

**原文两处说法不一致。**

1. Listing 2 的注释写最小堆「按在途计数作键」（PDF p. 7），正文却说计数是「自注册以来被分配的总数」（PDF p. 9）。前者是「最少在途」调度，后者是「累计轮询」调度：一个后端上的任务早早跑完，按在途计数它会立刻排到前面，按累计计数不会。论文没有说实际实现是哪一种。
2. 正文先说计数「按任务加一而非按调用」，紧接着又说 $w_s$ 统计的是「推理调用总数」（PDF p. 9）。结合上下文应理解为按任务计数。

**收益。** 把负载均衡换成「给每台 LLM 服务器分同样多的实例」，GPU 利用率从 78% 掉到 42%，吞吐从 0.37 掉到 0.25 实例/秒（PDF p. 13，Table 3），吞吐下降 32%（我们的计算），是所有消融项里最大的一笔。

**代价与边界。** 按任务计数均衡的是任务数，不是 token 数：一个跑满 50 轮、每轮上下文几万 token 的任务，和一个三轮就结束的任务，在堆里都算 1。粘性换来了前缀缓存，就放弃了细粒度均衡，论文没有测由此带来的不均衡有多大。checkpoint 交换也留了两个问题没回答：在途任务后半段用的是新权重还是旧权重，取决于推理服务是原地重载还是另起新实例，论文没写；`/clear_llm_server` 之后、`/add_llm_server` 之前后端池为空的那段时间，新调用阻塞、报错还是重试，也没写。

**可迁移启发。** 有前缀缓存的推理负载，均衡的单位是**会话**，不是请求。后续请求强依赖前序请求在服务端留下的状态时，把序列固定到一台机器上的收益，通常大于逐请求均衡的收益。要补的是对会话大小的估计，不是退回逐请求均衡。

## 核心设计四：token 进、token 出

**旧问题。** 轨迹若以纯文本在训练链路里传递，重新分词可能有损：得到的 token 序列和 rollout 时实际生成的不一样，造成意料之外的离策略偏差（PDF p. 9）。论文引 Agent Lightning 团队 2025 年的博客，称之为**重分词漂移（re-tokenization drift）**（PDF p. 2、p. 9）。

论文没有解释漂移为什么会发生。那篇博客（外部补充，[vLLM 博客，2025-10-22](https://vllm.ai/blog/2025-10-22-agent-lightning)）列了三个来源：同一段文字有多种切法，生成时的切法和再编码的切法可能不同；工具调用被解析成对象再渲染回文本，空白和格式可能变了；不同框架的聊天模板略有差异。

**新设计。** token id 成为贯穿整个训练过程的规范表示（PDF p. 9）：rollout worker 把 `prompt_ids` 直接发给推理后端，收回 `response_ids` 与逐 token 对数概率；每条消息额外带 `input_ids`、`output_ids`、`logprobs`，生成时填好，之后原样传递；多轮里，先前 assistant 回合保留原始 token id 直接拼进输入缓冲，只有新消息（比如环境观察）才被分词后追加。于是交给训练器的每个 token id 都与 rollout 时产出的完全一致。

**边界。** 它保证的是**模型自己生成的 token** 不被改写。环境观察本来就不是模型生成的，分词后追加是唯一可行的做法。训练器算对数概率时，系统提示与角色标记的拼接是否与 rollout 侧逐 token 一致，也就是聊天模板那一层，论文没有讨论。

**可迁移启发。** 两端要对同一串东西算概率，就必须拿到同一串离散符号，不能是「等价的文本」。任何「生成 → 序列化 → 反序列化 → 再评分」的链路都要问一句：回来的是原物还是等价物？

## 核心设计五：免 root 的沙箱，和工具后端的三处减法

### SingularityRuntime

HPC 集群出于安全考虑通常禁用 Docker 守护进程，要求用户进程在 Slurm 之类的调度器下以非 root 身份运行。论文实现了一个不需要常驻守护进程、完全作为非特权用户进程运行的容器系统（PDF p. 6）：

- **隔离与端口。** 每个容器作为子进程在自己的会话里启动，关闭时先 SIGTERM、必要时 SIGKILL。每个容器由线程安全的分配器拿到一个 `127.x.x.x` 范围内唯一的回环 IP，同一节点上许多容器不抢端口。
- **两个标志。** `--fakeroot` 给容器模拟的 root 权限，用来装软件包；`--network none` 可选地断外网，把 rollout 与外界干扰隔开。
- **镜像。** 打包成单文件的 `.sif`，适合没有常驻守护进程的 Slurm 共享文件系统。配套的构建器从 Jinja2 模板生成镜像，三种缓存模式：`Scratch` 每次全量重建，`Versioned` 在基础镜像与框架版本不变时复用，`Lock` 在依赖锁文件相同时复用。GUI 任务用的 QEMU 虚拟机可以给构建器提供自定义定义文件，不改核心逻辑。

这一节没有对应的消融：论文没有拿 Docker 版本做对照，在禁 Docker 的集群上也做不了。`--fakeroot` 依赖集群开启 Linux 用户命名空间（外部常识），这是管理员的决定，论文没有讨论。

### 工具后端的三处减法

每次工具调用对 Agent 都是同步阻塞的，一条轨迹几十次调用，单次延迟直接累加进总时长；高并发下这笔开销可能盖过 LLM 推理，成为首要瓶颈（PDF p. 6）。三处改动（PDF p. 6–7）：

| 工具 | 传统做法 | ProRL Agent 的做法 |
|---|---|---|
| Bash | 命令经 tmux 会话转发，承担终端复用开销 | 基于 `ptyprocess` 的直接伪终端，没有 tmux 这一层 |
| IPython | 经 Jupyter kernel gateway，同机也有一次网络往返 | 通过内核的进程内 API 直连，并保持内核持久，前一步的变量与导入后续可用 |
| 动作通道 | Agent 进程到容器内执行服务器走 TCP 回环，同 IP 的进程只能靠端口区分 | 换成 Unix domain socket，消息直接经内核传递，不占端口 |

**收益。** 把 Bash 换回 OpenHands 原版，平均动作时间从 0.42 秒涨到 0.78 秒，吞吐从 0.37 降到 0.29 实例/秒，GPU 利用率从 78% 降到 68%（PDF p. 13，Table 3）。动作时间涨了 86%，吞吐只掉 22%（我们的计算）：shell 动作只是总耗时的一部分，LLM 推理和其他阶段摊薄了它。IPython 直连与 UDS 的单独收益没有测。

**可迁移启发。** 在「模型想一步、环境执行一步」的串行链路里，环境侧每一毫秒的固定开销都要乘以轮数。先砍掉每次调用都要经过、却只为通用性存在的中间层。

## 任务生命周期：服务和函数的区别

这四条都很短，却是「服务」与「进程内函数」的区别所在（PDF p. 9）：

- **按阶段计时。** 每个任务一个 `PausableTimer`，只在 init、run、eval 活跃时累计，不计队列等待。任务不会因为前面排队的人多而被判超时。
- **取消。** 训练器随时可以 `POST /cancel`。服务把任务标记为丢弃，取消正在执行的异步任务，立即关闭关联容器，并置完成事件让等待中的 HTTP 处理器返回。用途是训练器攒够有效样本后丢弃未完成的 rollout。
- **失败隔离。** 每段一个专门的异常回调，失败时填兜底结果并置完成事件，单个失败的 rollout 不会卡住共享的工作池。
- **优雅关闭。** 收到 `POST /stop`，取消所有在途任务，按进程组扫描终止 Singularity 进程，排空工作池，不在节点上留下孤儿容器。

在共享 Slurm 集群上，最后一条最容易被低估：作业结束后留下的孤儿进程会继续占别人的节点。

## 接上训练器：两级分配与高效 DAPO

论文实现了对 veRL 与 NeMo RL 两个训练器的支持（PDF p. 10）。训练器一侧还做了一层分配：把 LLM 服务器分给各个 rollout 服务实例，先按 IP 匹配优先分给同一物理节点上的实例以减少网络延迟，剩下的按轮询分配保持全局均衡（PDF p. 10）。这说明实际部署是**多个** rollout 服务实例，各自持有一部分推理后端。

核心算法是 DAPO（PDF p. 10）。DAPO 会过滤「零方差 prompt」：同一道题的 rollout 奖励全相同（全对或全错），没有梯度信号，直接扔掉，对应 DAPO 一篇里的动态采样。单轮数学题上这很便宜，多采几道就是；Agent 任务上不便宜，因为 rollout 长、异步、昂贵。

![Figure 3 以 n = 4 为例对比两种实现：上半 Basic Implementation 分 Batch 1、Batch 2 两批，第一批只凑到 Prompt 1、2 两个有信息量的 prompt，Worker 1、2 提前做完后灰色空等到批末，第二批再发 Prompt 5–8，其中 7、8 整段是浪费；下半 Efficient Implementation 三个 worker 连续接活，Prompt 1、2、5、6 凑够 4 个有信息量的 prompt，只在 Worker 2 末尾剩一小块灰色。](/reports/ProRL-Agent/fig3-efficient-dapo.png)

朴素做法按批来：要 $n$ 个 prompt，滤掉没信息量的，再触发新一批，直到攒够 $n$ 个有信息量的。论文说它低效在三处：同步等待让 worker 空转，为了凑数多生成超出目标的 rollout，批末丢弃未完成的 rollout 又是浪费（PDF p. 10）。改成异步补充，三条规则（PDF p. 10）：

1. **持续吞吐**：任务队列一空就立刻补；
2. **提前终止**：攒够目标数量的有信息量 prompt，就终止其余活跃任务；
3. **跨迭代保留**：未完成的任务带到下一轮，保留部分进度。

**我们如何解释它：两个没回答的问题。**

- **提前终止和跨迭代保留怎么共存？** 如果终止就是 `/cancel`，它会关容器、释放资源（PDF p. 9），被取消的任务没有进度可保留；如果保留，就不是终止。一种可能的读法是「停止补充新任务，让在跑的自然跑完并计入下一轮」，论文没有这么写。
- **跨轮保留的轨迹是旧策略生成的。** 在第 $t$ 轮开始、第 $t+1$ 轮才完成的轨迹，进入第 $t+1$ 轮的梯度，就是陈旧度为 1 的离策略样本。AReaL 为这种样本设了可调上界并改了 PPO 目标，Laminar 把陈旧度变成由系统动力学决定、可以观测的量；**ProRL Agent 完全没有讨论陈旧度**，没有上限、没有修正、没有测量。它把这个问题原样留给了训练器。

**收益。** 去掉「陈旧任务清理」、改为等所有任务完成，吞吐从 0.37 降到 0.30 实例/秒，GPU 利用率从 78% 降到 65%（PDF p. 13，Table 3），吞吐下降 19%（我们的计算）。这一项对应的是提前终止。

3. **没有标准差、重复次数、评测温度和上下文上限。**

| ✓ | ✓ | | 0.42 | 65% | 0.30 |

三个对照组的做法：去负载均衡改为给每台 LLM 服务器分同样多的实例；去 Efficient Bash 改用 OpenHands 原版 Bash；去陈旧任务清理改为等所有任务完成（PDF p. 13）。相对全开配置，吞吐分别掉 32%、22%、19%（我们的计算）。

论文的归因是：负载均衡和陈旧任务清理靠提高 GPU 利用率，Efficient Bash 靠缩短动作时间（PDF p. 13）。表里最值得记的是第二行：看上去「公平」的均分实例，把 GPU 利用率压到 42%。这是 Agent 负载方差极大的最直接量化证据。

消融模型写作「Qwen3-14B-Instruct-2507」（PDF p. 13）。Qwen 官方在 Hugging Face 上发布的 2507 系列 Instruct 模型只有 4B、30B-A3B、235B-A22B 三档（外部核对，见文末），没有 14B；这个名字多半是笔误，实际模型论文没有交代清楚。

## 实验四：扩展性，「几乎线性」要打折扣

![Figure 5 是 rollout 吞吐对节点数的折线图，横轴 1、2、4、8 个节点，三条线：4B 约 0.36、0.66、1.12、1.67；8B 约 0.35、0.65、0.62、1.71，在 4 节点处比 2 节点略低；14B 约 0.26、0.47、0.77、1.26，单位是实例每秒。](/reports/ProRL-Agent/fig5-scaling.png)

论文在软件工程任务上测 1、2、4、8 个节点的 rollout 吞吐，结论是「几乎线性增长」，扩展开销很小（PDF p. 13，Figure 5）。

对照图算：节点翻 8 倍，三档吞吐约涨 4.6、4.9、4.8 倍，扩展效率约六成（读自 Figure 5，倍数是我们的计算），「几乎线性」偏宽松。8B 那条在 4 节点处回落到略低于 2 节点，论文没有解释。一个「节点」里有几张卡、rollout 服务和推理引擎怎么摆，论文没有写；如果一个节点是 8 张卡，Figure 5 里 14B 单节点约 0.26 实例/秒，和 Table 3 在 8 张 H100 上的 0.37 也对不上，两处用的 14B 模型可能不同。

## 限制与未公开信息

结论只把「更丰富的环境」与「集群规模的健壮性」列为未来工作（PDF p. 14）。读完要补的缺口：

1. **没有跨框架的性能对比。** Table 1 是特性对比，Table 3 是内部消融。
2. **陈旧度完全没讨论。** 跨轮保留的轨迹、checkpoint 交换时的在途任务，都会把旧策略的样本送进新一轮梯度。
3. **checkpoint 交换的实现没写**：推理服务原地重载还是另起新实例。
4. **最小堆的键是「在途」还是「累计」**，注释与正文不一致。
5. **三个工作池的大小、超时阈值、实验用的最大轮数**都没给（50 轮只出现在附录示例图里）。
6. **32 张 H100 怎么在训练、推理、rollout 服务之间划分**没写；附录示例是训练侧 4 节点 × 8 卡、rollout 服务另起在 CPU 或 GPU 节点上（PDF p. 18），那是示例，不是实验配置。
7. **评测口径没写**：SWE-Bench Verified 的 harness、上下文上限、采样温度、重复次数。
8. **三个新域没有下游分数**，STEM 曲线起点与正文不符。
9. **扩展效率只有定性描述**，节点定义没写。
10. **IPython 直连与 UDS 的单独收益没测。**
11. **容错只到「单个任务失败不卡池」**，整台 rollout 节点挂掉时在途任务能否恢复，没写。

## 与后作 Polar 的分工

同一团队两个月后发布的 Polar（本站 Polar 一篇）自称重写了 ProRL Agent（Polar 原件 p. 1）。两篇放在一起看，变与不变很清楚：

| | ProRL Agent（本篇） | Polar |
|---|---|---|
| 服务边界 | 训练器与 rollout 服务之间，HTTP | 同样是 rollout 即服务，任务 API 与训练循环分离 |
| 用户要写什么 | 一个 `AgentHandler`，`run()` 里就是 Agent 循环（PDF p. 5） | 一个启动原生可执行文件的 harness 适配器，模型调用由代理从外面记录 |
| 分阶段 | INIT → RUN → EVAL 三池三队列（PDF p. 7–8） | 网关内多个隔离池加一个有界缓冲，执行与评估之间插入轨迹重建 |
| token 保真 | rollout worker 直接收发 token id（PDF p. 9） | 在模型 API 边界截下采样 token，再重建轨迹 |

两份原件的自我评价有一处值得对照。本篇 Table 1 给自己在「不绑定脚手架」一栏打 ✓（PDF p. 3），理由是脚手架可替换而不影响训练基础设施（PDF p. 5）；Polar 的对照表给 ProRL Agent 在「原生 harness 无关」一栏打 ✗，理由是它要用户在服务里实现 handler。两边的定义不同：前者说训练侧不受影响，后者说 harness 不必被改写。Polar 那张表还给 ProRL Agent 的「异步 RL」打了 ✓，而 Polar 对这一栏的定义要求有明确的策略版本或陈旧度处理；本篇原件里找不到这类机制。

## 与同方向几篇串起来读

| | HybridFlow | AReaL | Laminar | ProRL Agent |
|---|---|---|---|---|
| 回答的问题 | 多个模型的 RL 数据流怎么写 | 生成与训练异步后，陈旧数据怎么接 | 全局权重同步点能不能取消 | Agent 的执行环境怎么从训练进程里搬出去 |
| 解耦的是什么 | 控制流与计算 | 生成 GPU 与训练 GPU | 每条轨迹与全局同步点 | Agent 循环、沙箱、评估与训练器 |
| 生成引擎归谁 | 训练框架内 | 独立的生成 worker 池 | rollout 副本 | 训练框架（服务只持有地址） |
| 陈旧度 | 无（同步） | 可调上界，并改目标函数 | 不设上界，由系统动力学决定、实测很小，不做修正 | 没讨论 |

三条接续关系：

1. **ProRL Agent 站在 HybridFlow 的编程模型上。** 它支持的训练器之一是 veRL（PDF p. 10），附录里的驱动进程做的正是单控制器循环：准备批、生成、算优势、更新 actor（PDF p. 18）。它只把「生成」里属于 Agent 的部分挖出去，变成 HTTP 调用。
2. **AReaL 与 Laminar 解决的问题它没碰。** 推理引擎仍在训练器手里，权重什么时候换、换时在途轨迹算什么，仍要训练器回答。Laminar 报告多轮编码任务里环境交互占 30.2% 的时间；ProRL Agent 做的是把这部分搬到另一组机器上，长尾还在，只是不再占训练 GPU。
3. **它们可以叠加。** 一个训练器完全可以用轨迹级异步管生成与训练，同时用 ProRL Agent 这样的服务管沙箱与工具。论文没有做这种组合。

## 可迁移启发

1. **瓶颈资源不同的两件事，不要放进同一个进程。** 判据不是代码量，是资源类型：rollout 是 I/O 活，训练是 GPU 活（PDF p. 1）。
2. **服务边界放在协议最薄的地方。** 六个端点、两种数据（任务实例进，轨迹加奖励出），两边才能各自演化。后作 Polar 把边界再往外推到模型 API 调用上，协议更薄，可替换性更强。
3. **按阶段分 worker，不按作业分。** 耗时方差大的那一段只让自己排队。数据管道的「拉取 → 转换 → 校验」、CI 的「拉镜像 → 跑测试 → 传产物」都适用。
4. **有会话状态的负载，均衡的单位是会话。** 反例就在消融里：均分实例把 GPU 利用率压到 42%（PDF p. 13）。
5. **离散符号跨系统传递时，传原物不传等价物。** 文本到 token 的映射不是一一对应的。
6. **环境侧的固定开销要乘以轮数。** 先砍每次调用都要经过的中间层：tmux、kernel gateway、TCP 回环。
7. **「等最慢的那个」是可以量化的开销。** 去掉等全部完成的屏障，吞吐多出 19% 的余量（PDF p. 13，我们的计算）。先测它值多少，再决定要不要为此接受离策略样本。
8. **运维约束是设计输入。** 免 root、无守护进程、按进程组清理孤儿，决定了这套东西能不能在真实的共享集群上跑起来。

## 关键词回看

- **rollout 即服务（rollout-as-a-service）**：把从建环境到评分的整条轨迹生成做成独立 HTTP 服务，训练器只提交任务、收回结果。
- **rollout 级解耦**：解耦的是 Agent 执行，不是推理引擎。
- **AgentHandler**：`init` / `run` / `eval` 三个生命周期方法，加三个按阶段的异常回调与 `final_result`。
- **三阶段异步流水线**：INIT、RUN、EVAL 各一条 FIFO 队列和一个独立工作池；RUN 结束先释放容器再进 EVAL。
- **LLM 后端池与 min-heap**：选计数最小的后端，整个任务粘在同一后端上以复用前缀缓存；`/clear_llm_server` 加 `/add_llm_server` 完成 checkpoint 交换。
- **token 进、token 出**：训练链路全程传 token id 与对数概率，旧 assistant 回合原样拼接，只有新消息被分词，用来消除重分词漂移。
- **SingularityRuntime**：无守护进程、非特权的容器运行时；`--fakeroot`、`--network none`、`.sif` 单文件镜像、三种构建缓存模式、每容器回环 IP。
- **PausableTimer**：只计活跃阶段、不计排队的超时计时器。
- **异步补充**：持续吞吐、提前终止、跨迭代保留，替代按批凑够有信息量 prompt 的朴素 DAPO 实现。
- **实例/秒**：论文的吞吐单位，每秒完成的任务实例数，不是 token 数。

# RLM：别把超长 prompt 塞进窗口，把它放进 REPL 当变量，让模型写代码递归调用自己

<!-- release-date: 2025-10-15 -->

> 本文依据 MIT CSAIL 的 **Recursive Language Models**，arXiv:2512.24601v3，2026-05-11 修订，共 43 页：正文 pp. 1–10，参考文献 pp. 10–15，附录 pp. 16–43。作者 Alex L. Zhang、Tim Kraska、Omar Khattab。页码均指这份 PDF 自身的页码。文中会区分三件事：**论文明确写了什么**、**我们怎么解释它**、**哪些是外部资料或本文换算**。

## 读前先把几个词说成人话

这篇论文几乎不改模型权重，讲的是怎么「用」模型。它借了不少编程和 agent 的词，先说清楚。

- **上下文窗口（context window）**：一次模型调用能读进去的 Token 上限。论文实验里 GPT-5 是 272K Token（PDF p. 1）。
- **上下文腐烂（context rot）**：窗口还没满，prompt 一长，模型准确使用其中信息的能力就往下掉（PDF p. 1，引 Chroma 的同名报告）。不是看不见，是越看越糊。
- **压缩（compaction）**：上下文快满时把旧内容总结成短摘要，腾出位置。论文认为这是当时最流行的通用长上下文办法（PDF p. 2）。
- **REPL（Read-Eval-Print Loop，读–求值–打印循环）**：一个持久的编程环境。写一段代码，执行，打印结果，变量留着下次还能用。论文用的是 Python REPL。
- **根模型（root）与子调用（sub-call）**：一次 RLM 调用里最外层做决策的模型叫根模型；它在代码里再发起的模型调用叫子调用。
- **递归深度（recursion depth）**：depth 0 只有根模型，不能子调用；depth 1 可以调普通 LLM；depth 大于 1 时，子调用本身也可以是一整个 RLM（PDF p. 5）。
- **CodeAct**：一种让模型在 ReAct 循环里写代码、执行代码的 agent 写法。它和 RLM 的区别是 prompt 仍然直接给模型读（PDF p. 5）。
- **任务复杂度随长度怎么涨**：论文评测的核心视角。找一根针，要找的信息量不随长度变，记作 $O(1)$；每一行都要看，工作量随长度线性增长，$O(N)$；每一对行都要比，$O(N^2)$（PDF p. 4–5）。

论文自己造的名字只有一个：**Recursive Language Model（RLM，递归语言模型）**。它对外仍是「字符串进、字符串出」，对内不把长 prompt 喂进 Transformer，而是把它当成外部环境里的一个变量（PDF p. 2）。

## 一句话先说清

今天处理超长材料，主流办法有三条：把窗口做大、把旧内容摘要掉、让 agent 去文件或语料里检索。它们共享一个默认动作：**总有一个时刻，模型必须把当前要处理的文本放进自己的窗口。** 窗口满了就只能摘要，摘要就要丢细节。

RLM 拆掉的就是这个默认动作。

![RLM 把整段 prompt 装进 REPL 的变量，根模型只看元数据并写代码；代码在循环里对片段发起子调用，结果存进变量，最后返回 Final 变量的值。](/reports/Recursive-Language-Models/figure2-rlm.svg)

图上黄色的 hist 只装常数大小的东西；绿色的变量可以任意大。模型的窗口只用来「想下一步写什么代码」，不再用来「装材料」。这是一种 **推理期扩展（inference-time scaling）**：多花测试时计算，换来远超窗口的有效输入与输出（PDF p. 2）。

论文的结论分三块：

1. **能跑到窗口之外，而且在窗口之内也更好。** 输入超过 GPT-5 窗口一个数量级以上（BrowseComp-Plus 的 6M–11M Token）仍有 91.3 分；在信息密集的任务上，即使输入放得进窗口，RLM 也明显好过直接读（PDF p. 1、p. 6）。
2. **比常见支架好，花费同一量级。** 以 GPT-5 为底，四个任务的中位提升：相对压缩 26%，相对带子调用的 CodeAct 130%，相对 Claude Code 13%（PDF p. 1）。
3. **可以训。** 只用 1000 条左右、来自无关领域的蒸馏轨迹微调 Qwen3-8B，得到的 RLM-Qwen3-8B 在四个任务上相对未训练的同支架版本中位提升 28.3%，还快 3 倍以上（PDF p. 3、p. 8）。

要带走的只有一条：**窗口是模型一次能读的预算，不是系统一次能处理的预算。** 把材料留在窗外，让模型用代码决定每次读哪一段、对哪一段再调用自己，有效上下文就能跟着推理计算一起扩展。

## 主要矛盾：窗口是硬上限，腐烂是软上限，而现有支架都还在窗口里干活

论文开篇给出两层问题（PDF p. 1–2）。

**第一层，窗口不够大，而且不够好。** 前沿推理模型的窗口有限；就算没满，也会有上下文腐烂。长程任务要处理的 Token 可能是上千万甚至上亿（PDF p. 1–2）。作者承认窗口会随训练、架构和基础设施的改进继续变长，但他们关心的是：能不能不等这些，就把通用模型的有效上下文放大几个数量级。

**第二层，现有的通用办法都绕不开窗口。**

- 压缩默认「前面的一些细节可以忘掉」，对需要随时回看全文的任务表达力不够（PDF p. 2）。
- 代码 agent 与检索 agent 把文件系统或语料库当环境，但取回来的片段仍然要塞进窗口，塞满了还是要压缩（PDF p. 2）。
- 让模型把自己当子 agent 调用的做法（如 Claude Code 的 subagent），子调用是模型用自然语言「说出来」的，受单次输出长度限制，只能委托少数几件事（PDF p. 2–3）。

于是矛盾是：

> 材料放进窗口会腐烂、会撑破；放在窗外，现有办法又只能一次取一小块回来读，或者只能口头委托几件事。能不能让模型**不读全文，却能对全文的每一部分都做到语义处理**？

## 核心设计：三个看似细小、却决定表达力的选择

论文用两段伪代码对比来讲方法（PDF p. 4）。Algorithm 1 是 RLM；Algorithm 2 是一个「看起来差不多」的支架：它也有代码执行、也有子 LLM、也能搜索外部数据。两者的差别只在三处，作者把 Algorithm 2 的三处标成 Flaw 1–3。

| | RLM（Algorithm 1） | 常见支架（Algorithm 2） | 差别的后果 |
|---|---|---|---|
| prompt 放在哪 | REPL 的变量里；根模型只拿到长度、前缀、怎么取片段 | 直接放进模型的历史 hist | 后者继承窗口上限，满了只能压缩（Flaw 1） |
| 答案从哪出 | 代码把答案拼进变量 Final，返回变量的值；也允许模型直接写答案 | 模型用 Finish 动作直接说出来 | 后者的输出不能超过单次生成长度（Flaw 2） |
| 子调用怎么发起 | REPL 里的代码调用 `llm_query`，可以写在任意大的循环里 | 子 LLM 是一个单独的动作，模型每次口头发起一个 | 后者只能委托几件显式说出的事，做不到对全文每一片、每一对都调用一次（Flaw 3） |

（PDF p. 3–4）

**为什么第三条最要紧。** 论文说得很直白：代码必须能在程序构造出的 prompt 变换上调用模型，比如在循环里对每一片调用一次，结果存成变量。这样一次 RLM 调用就能发起 $\Omega(|P|)$ 乃至 $\Omega(|P|^2)$ 次语义处理（PDF p. 3–4）。模型口头一次委托一件，永远到不了这个量级。

**还有一个容易忽略的细节，在脚注里。** 每轮执行完，只把 stdout 的元数据（一小段前缀和长度）追加进根模型的历史，而不是完整输出。作者说这是关键：它逼着模型用变量和子调用去管理长字符串，而不是把自己的窗口弄脏。若每轮截到 $c$ 个 Token，根模型最多能跑 $K/c$ 轮，$K$ 是窗口大小，但每轮都能发起任意多子调用（PDF p. 3 脚注 2）。

**具体实现。** 给模型一个 Python REPL，子 LM 或子 RLM 的调用都作为模块放进去；初始 prompt 存成变量；模型循环交互直到给出最终答案，答案可以是 REPL 里的某个变量，也可以是模型自己写的一段话；print 的输出会被截断（PDF p. 4）。附录的提示词里，两种交卷方式写作 `FINAL(答案)` 与 `FINAL_VAR(变量名)`（PDF p. 19）。

**我们如何解释它。** 三条合起来，是把「读」「写」「分派」三件事都从模型的窗口里挪到了代码里。模型的窗口里只剩计划。这和操作系统里「进程只拿一个文件句柄，不把整个文件读进寄存器」是同一个思路：不是让寄存器变大，而是让程序学会按需去读。

### 可迁移启发

设计 agent 支架时，先问三个问题：长输入是不是一进来就被塞进了模型历史？最终输出是不是只能靠模型一口气说出来？子调用是不是只能由模型一次一次口头发起？三个里只要有一个是「是」，这个支架的上限就被窗口或单次输出长度锁住了。

## 评测怎么设计：让任务复杂度跟着长度一起变

论文的一个判断是：模型的「有效窗口」不能脱离任务来谈，越复杂的任务，在越短的长度上就开始掉（PDF p. 4）。所以四个任务按「要处理的信息量随长度怎么涨」来挑（PDF p. 4–5）：

| 任务 | 测什么 | 复杂度随长度 | 规模与指标 |
|---|---|---|---|
| S-NIAH | 在大量无关文本里找一个短语或数字，仿 RULER 的单针任务 | $O(1)$ | 50 题，只出现在 Figure 1 |
| BrowseComp-Plus（1K 文档） | 深度研究式多跳问答，要从多篇文档拼证据 | 常数篇文档，但要多跳 | 随机抽 150 题，每题给 1000 篇文档（含金标与证据文档），报正确率；输入 6M–11M Token |
| OOLONG（trec_coarse） | 给每条问题打语义标签，再做聚合统计 | $O(N)$ | 50 题，输入 131K Token |
| OOLONG-Pairs | 作者改造的 OOLONG，要列出全部满足条件的用户对 | $O(N^2)$ | 20 题，报 F1，输入 32K Token |
| LongBench-v2 CodeQA | 代码仓理解的多选题 | 固定数量的文件 | 输入 23K–4.2M Token |

OOLONG-Pairs 是作者自建的。附录 D.1 列出了全部 20 道题，并解释了为什么它一定是平方复杂度：很多「成对」问题其实可以用容斥原理线性地数出来，所以每题都要求**列出**所有满足条件的对，而不是只数个数（PDF p. 26–30）。

先看这种设计能说明什么。

![GPT-5 直接读时，S-NIAH 始终满分，OOLONG 与 OOLONG-Pairs 随长度迅速下滑，超过 272K 就没有分数；换成 RLM(GPT-5) 后，两条密集任务曲线下滑平缓，并一直延伸到 1M。](/reports/Recursive-Language-Models/figure1-rlm.svg)

同一个 GPT-5，任务越密，掉得越早：S-NIAH 到 262K 都是满分，OOLONG-Pairs 在 33K 就几乎归零（本文从原图读到）。这印证了「有效窗口取决于任务」这一判断（PDF p. 4 脚注 3、p. 7）。论文的原话是：输入超过 $2^{14}$ 之后，RLM 一直好过 GPT-5（PDF p. 7）。

**我们如何解释它。** 右图最有信息量的不是 1M 处还有分，而是 8K 处 RLM 在 OOLONG 与 OOLONG-Pairs 上都比 GPT-5 低几分。短输入时，把材料切开再分派有额外的出错机会；RLM 的优势是随长度和密度一起出现的，不是在所有长度上都占优。

## 对照组：论文在和谁比

两个骨干模型（PDF p. 5）：

- **GPT-5**（中等推理强度）做根模型，**GPT-5-mini** 做子调用模型。作者说这个组合在能力与子调用成本之间比较平衡。
- **Qwen3-Coder-480B-A35B**，成本按 Fireworks 的价格算。

对照方法都是任务无关的通用办法，每种方法的提示词在所有任务上固定不变（PDF p. 5、p. 18）：

- **基座模型直接读**。
- **CodeAct + BM25**：带检索器的代码 agent。
- **CodeAct + 子调用**：REPL 里也能调子 LLM，但 prompt 直接给模型读，不放进变量。这正好是 RLM 去掉 Flaw 1 之前的样子。
- **压缩 agent**：满了就摘要，单篇超窗口就切块再摘要。GPT-5 这组为了控制成本，用 GPT-5-nano 做摘要、GPT-5 给最终答案（PDF p. 5）。
- **OpenCode 与 Claude Code**，各有「直接把材料当 prompt」与「把材料放进文件」两种。Claude Code 是为自家模型设计的，所以用的是 Claude Opus 4.1 配 Claude Code v2.0.0（PDF p. 5）。
- **RLM depth 0–3**。depth 0 就是「有 REPL、没有子调用」，是拆开看两件事各自贡献的关键消融。

### 摘要里的三个中位数是怎么来的

摘要说以 GPT-5 为底，RLM 相对压缩中位提升 26%、相对 CodeAct + 子调用 130%、相对 Claude Code 13%（PDF p. 1）。用上表的 RLM depth 1 逐任务算相对提升，再取四个任务的中位数（本文换算）：

- 相对压缩 agent：CodeQA +6.9%、BrowseComp-Plus +29.5%、OOLONG +21.7%、OOLONG-Pairs 从 0.1 到 58.0。中位数约 25.6%，对得上 26%。
- 相对 CodeAct + 子调用：+158%、对方 0 分、+40%、+104%。中位数约 131%，对得上 130%。
- 相对 Claude Code：只有「材料放文件」那一版才对得上，+0%、+8.7%、+16.7%、约 8.9 倍，中位数约 12.7%。

读这三个数要知道两件事。第一，**「相对 Claude Code」是跨模型比较**：一边是 GPT-5 加 GPT-5-mini，一边是 Claude Opus 4.1。第二，Table 1 没有 S-NIAH，四个任务里有两个的对照方偶尔撞上长度上限。中位数是一个很宽容的汇总方式，它不受 OOLONG-Pairs 那种上百倍的极端值影响，也不告诉你最差的那个任务差多少。

### 表里还能读出的三件事

**第一，REPL 负责「装得下」，递归子调用负责「读得细」。** 这是论文的 Observation 2（PDF p. 7）。depth 0 已经能处理超窗口的输入：GPT-5 组在 BrowseComp-Plus 上 88.0，与 depth 1 的 91.3 差得不多。但到 OOLONG 与 OOLONG-Pairs 这种每行都要做语义判断的任务，depth 0 只能靠关键词启发式，打不过能对每一行调用子模型的 depth 1（PDF p. 7）。反例也有：Qwen3-Coder 在 CodeQA 上 depth 0 的 66.0 高于所有带子调用的版本。

**第二，深度的效果取决于根模型。** GPT-5 组在 OOLONG-Pairs 上随深度单调上升，43.9、58.0、65.5、76.0；Qwen3-Coder 组加深度反而常常变差。论文在第 5 节给出的解释是 Qwen3-Coder 语法错误多，子 RLM 会把错误一层层传下去（PDF p. 9）。

**第三，「把材料放进文件」本身就是一大步。** OpenCode 与 Claude Code 的两种版本对比非常鲜明：GPT-5 组的 OpenCode 在 BrowseComp-Plus 上从 0.0 跳到 94.0，甚至高过 RLM。这说明 RLM 的收益里，有很大一块来自 Flaw 1 的修正，即不把材料直接塞给模型；递归子调用的额外价值，主要体现在 OOLONG-Pairs 这类最密集的任务上：那里放文件的 OpenCode 只有 4.8，RLM 有 58.0–76.0。

### 另外三条观察

**成本（Observation 4）。** 平均成本与多数基线同一量级甚至更便宜。附录 Figure 11 按分位数画成本：中位数上 RLM 与基座相当甚至更便宜，但 95 分位急剧升高，是少数找不到答案、一直转下去的长轨迹拉高了均值（PDF p. 7、p. 40–41）。BrowseComp-Plus 上，若按线性外推让 GPT-5-mini 直接读 6M–11M Token，要 \$1.50–\$2.75；RLM(GPT-5, depth 1) 平均 \$0.99，还比压缩与检索基线高 29% 以上（PDF p. 6）。

**耗时。** 论文特意给耗时加了限定：所有子调用都是阻塞、串行的，耗时高度依赖机器、API 延迟与实现（PDF p. 7）。附录 Figure 12–13 显示 RLM 的耗时分布拉得很开，95 分位极长，主要花在串行的子调用上，作者认为异步调用与超时逻辑能解决（PDF p. 41）。

**信息密集任务在窗口之内也受益。** OOLONG 输入只有 131K，放得进 GPT-5 的窗口，RLM depth 1 仍比直接读高：Qwen3-Coder 组 36.0 到 48.0，即 +33.3%；GPT-5 组 44.0 到 56.0，论文写 +28.4%，按表算是 +27.3%（PDF p. 6，本文换算）。OOLONG-Pairs 上两个基座 F1 都只有 0.1，RLM 做到 58.0 与 23.1。

## 不只是长输入：长推理

Observation 5 用 LongCoT-mini 测另一种「长」：题目本身由许多互相依赖的子问题组成，一条思维链容易在中途丢掉部分结果或累积符号错误（PDF p. 7）。对照是原基准论文里最强的 GPT-5.2。

| 方法 | 总体 | 数学 | 化学 | 计算机 | 逻辑 | 国际象棋 |
|---|---:|---:|---:|---:|---:|---:|
| GPT-5.2 直接做 | 38.7 | 26.0 | 37.0 | 40.4 | 53.6 | 36.6 |
| GPT-5.2 + 分解提示 | 28.6 | 37.0 | 27.0 | 32.0 | 19.1 | 30.0 |
| RLM(GPT-5.2, depth 1) | 50.6 | 5.6 | 50.0 | 11.0 | 86.7 | 93.0 |
| RLM(GPT-5.2, depth 1) + 分解提示 | **65.6** | **32.0** | **52.0** | **46.0** | **99.0** | **99.0** |

（PDF p. 7 Table 2、p. 24 Table 3）

几点要一起读：

- 不加提示的 RLM 总分更高，但数学从 26.0 掉到 5.6、计算机从 40.4 掉到 11.0。它把逻辑和象棋这类可以程序化的题做得很好，在另一些题上反而更差。
- 加上「分解提示」后，RLM 让子 LM 先把题目抽成一张依赖图（DAG），再逐层把就绪的节点并行交给子调用，每个答案验证后才传给下游，最后只靠字典查找拼答案（PDF p. 24–26）。六个类别全部超过基座，总体提升 69.5%（PDF p. 7）。
- 同样的分解提示直接给 GPT-5.2（去掉子调用的部分），总分反而从 38.7 降到 28.6。附录的解释是：没有 REPL 这种能把子任务隔离开的机制，模型在一条思维链里执行分解会被搞糊涂（PDF p. 24）。
- 这组实验用的是 Prime Intellect 的 rlm-harness，与主实验的实现不同，交卷方式也不同（PDF p. 24）。

**我们如何解释它。** 分解提示的核心一句是「Orchestrate; don't solve」：根模型不做数学，只做调度、记账与核对（PDF p. 24）。这把 RLM 的「材料留在窗外」推广成了「中间结果也留在窗外」：每个子问题的答案存进字典，下游只拿验证过的值。它和长输入场景是同一个原理，只是被外置的东西从 prompt 变成了推理过程本身。

## 小规模训练：只教根模型怎么当 RLM

### 旧问题：小模型塞进 RLM 支架也几乎不会用

Qwen3-8B 放进 RLM 支架里，在长上下文任务上仍然很吃力（PDF p. 3）。附录 B 的负结果也写了：编码能力不够的模型当不好 RLM（PDF p. 17）。

### 新设计：叶子调用就是普通 LLM 请求，难的只是根模型

作者的判断是：一条 RLM 轨迹可以因为子调用而极长，但叶子上的子调用本质上就是普通的 LLM 请求，真正的门槛是学会当根模型——操作 REPL 里的 prompt、判断什么时候该子调用（PDF p. 5–6、p. 16）。所以训练只针对根模型。

配方（PDF p. 16）：

1. 用 RLM(Qwen3-Coder-480B-A35B) 在 750 道英文 LongBenchPro 题上采样，共 2250 条候选轨迹；子调用用的是 Qwen3-8B（PDF p. 5）。
2. 去掉得分为 0 或只有一轮的，剩 1072 条。
3. 把每一轮根模型的决策拆成一条 SFT 样本：输入是完整历史，输出是这一轮根模型写的东西。
4. 去掉超出 Qwen3-8B 窗口的轮次（按约 100K 字符近似），再用程序修补模板错误：16% 的轮次把 `FINAL` 用错，13% 的轮次错把 REPL 变量当 `FINAL_VAR` 的答案交。作者说这一步修补让蒸馏出的模型好了很多。
5. 用 prime-rl 训练，batch 64、300 步、48 个 H100 小时。

Figure 5 给了过滤前后的统计：轨迹数 2241 到 953，平均轮数 5.33 到 4.96，每轮输入约 9734 到 7941 Token、输出约 1032 到 910 Token（PDF p. 16）。正文把训练集说成「1000 条」（PDF p. 3、p. 5），与这些数字大致相当。

论文特意强调 LongBenchPro 是与评测任务「无关」的一组任务（PDF p. 8）。

### 收益：四个任务都涨，而且快得多

| 任务 | Qwen3-8B 直接读 | RLM(Qwen3-8B) | RLM-Qwen3-8B | 平均耗时（秒）：训练前 → 训练后 |
|---|---:|---:|---:|---|
| CodeQA | 4.00 | 26.00 | 32.00 | 272 → 86 |
| BrowseComp-Plus | 0.00 | 2.00 | 14.00 | 341 → 101 |
| OOLONG | 0.00 | 24.00 | 32.04 | 12449 → 1649 |
| OOLONG-Pairs | 0.07 | 4.26 | 5.17 | 5113 → 532 |

（PDF p. 8 Figure 3(a) 与 p. 17 Figure 6，数字读自两张图上的标注。耗时是 RLM(Qwen3-8B) 与 RLM-Qwen3-8B 的对比。）

相对未训练的 RLM(Qwen3-8B)，四个任务的相对提升是 +23%、+600%、+33%、+21%，中位数 28.3%，这就是摘要里的「28%」（本文换算，与 PDF p. 3 一致）。注意比较对象：是同一个 RLM 支架里训练前后的 Qwen3-8B，不是 Qwen3-8B 直接读。耗时降了 68%–90%，作者归因于决策更好、错误更少（PDF p. 8）。

摘要说它「在三个长上下文任务上接近 vanilla GPT-5」。对照 Table 1 的 GPT-5 直接读：CodeQA 32.00 对 24.0、OOLONG 32.04 对 44.0、OOLONG-Pairs 5.17 对 0.1（本文对照）。「接近」的说法在 OOLONG 上是宽松的。

### 长度外推：64K 上学，1M 上考

另一组实验用强化学习训练 Qwen3-4B-Instruct（论文写作 0527 版）当 RLM depth 1，任务是 MRCRv2：在一大段语料里找出并复述某段文字的多个实例（PDF p. 8）。只在 32K–64K、2 根针的切分上用可验证奖励的强化学习（RLVR）训练 150 步，batch 128、每题 4 条 rollout、每轮最多输出 4096 Token、最多 20 轮；每 50 步在 512K–1M、8 根针的切分上评估一次（PDF p. 17）。

Figure 3(b) 里，1M、8 针上的评估分从约 0.03 升到约 0.98，而 1M 窗口的 Gemini 3.1 Pro 在同一切分上约 0.26（PDF p. 8，本文从图上读到）。训练集比评估集短一个数量级以上、针也少，这是论文「长度外推」的依据。

### 代价与边界

作者自己称这是一次「小规模练习」，并认为要把 RLM 的潜力做满，需要更大的模型、更多更杂的样本、更多（最好是在线、同策略）的 rollout（PDF p. 16）。第 7 节把训练原生 RLM 称为可能的「新扩展轴」，但目前只有 8B 与 4B 两个点（PDF p. 9）。

## 轨迹里看到的：第一次怎么切，决定了很多

第 5 节和附录 E、F 从轨迹层面看 RLM 在做什么（PDF p. 8–9、p. 31–43）。

**常见模式。** 先探查，再分解，再对子任务发子调用。附录 Figure 8 截了三种典型片段：用正则代码过滤材料；把大段材料分批交给子调用去做语义判断；在长输出任务上，把子调用的结果在代码里拼成一个长答案（PDF p. 31）。

### 第一次分解会被系统提示里的例子撬动

Figure 4(a) 在 OOLONG 上比较了系统提示里放不同例子时，RLM(GPT-5) 第一次分解的对错与最终结果（PDF p. 8）。

| 系统提示里的例子 | 做对的 rollout（约） | 首次分解就错的 rollout（做对 + 做错） | 做错的主要原因 |
|---|---:|---:|---|
| 没有例子 | 23 | 11 + 21 | 首次分解错 |
| 一个正确例子 | 30 | 10 + 15 | 首次分解错 |
| 一个明确的例子 | 33 | 约 0 | 首次分解对，但子调用失败（16 条） |

（读自 PDF p. 8 Figure 4(a) 的柱上标注；图中未标数字的细条各约 1 条，所以合计是近似值。每行合计约 50 条，对应 OOLONG 的 50 题。）

论文的结论是：系统提示里的 RLM 轨迹例子能大幅改善总体表现与第一次分解，**哪怕例子和任务无关**；RLM 常能从一次错误的分解里恢复，但第一次分解对总体表现仍然很重要（PDF p. 8–9）。

**我们如何解释它。** 表的第三行说明了一件事：一旦分解对了，剩下的失败几乎都落在子调用上。瓶颈从「会不会切」移到了「子模型每一片做得准不准」。这也是论文训练时只训根模型、叶子用现成 LLM 的前提所在：根模型切得对，才轮得到叶子的质量。

### 语法错误会沿递归传播

Figure 4(b) 统计了 Table 1 里 depth 1 轨迹中至少出现一次语法或格式错误的比例：Qwen3-Coder 明显多于 GPT-5，在 OOLONG-Pairs 上几乎每条都有，而且做对的轨迹也常有（PDF p. 8–9）。这解释了为什么 Qwen3-Coder 加深度反而变差：子 RLM 把同样的错误带进每一层（PDF p. 9）。

### 子调用次数可以差两个数量级

同一道 OOLONG 题，Qwen3-Coder 会给每一行单独发一次子调用，一题几百到上千次；GPT-5 通常在十次量级（PDF p. 31、p. 37）。Figure 10 显示 Qwen3-Coder 在 OOLONG 做对的轨迹平均约 500 次子调用，Qwen3-8B 在做错的轨迹上反而调用更多（PDF p. 40）。附录 C 里给 Qwen3-Coder 的提示词因此专门加了一段：尽量把约 200K 字符打成一批，1000 行宁可分成 200 次而不是 1000 次调用；不加这句，它会对每样东西都发子调用，简单任务也要上千次（PDF p. 18–19）。

### 长输出走变量，但模型可能不交卷

![RLM 解 OOLONG-Pairs 时，先探查、再让子调用给每条打标签、再用代码筛用户并拼出全部用户对存进变量；附录 E.2 这条轨迹答案已在变量里，却反复重算五遍，最后交了根模型自己生成的错误答案。](/reports/Recursive-Language-Models/figure-rlm-pairs.svg)

这张图把两件事放在一起：RLM 能突破单次输出长度，靠的是把答案在变量里拼出来（Flaw 2 的修正）；而附录 E.2 的这条轨迹说明，当前模型并不总是会用这个能力。作者把原因归到两点：没有为这个模型专门调提示词，以及模型没有被训练成 RLM（PDF p. 36）。附录 B 也把「区分最终答案与中间想法很脆弱」列为负结果：模型有时会把计划当成最终答案交出去（PDF p. 17）。

另外三条轨迹（PDF p. 31–39）：

- **E.1**，RLM(GPT-5) 做 BrowseComp-Plus：1000 篇文档共约 8.3M Token。根模型先用带先验的关键词做正则搜索，在第 6 块里找到可疑片段，对它发一次子调用，得到答案后又用两次子调用复核，交出正确答案，整条轨迹花费 \$0.079。
- **E.3**，RLM(Qwen3-Coder) 做 OOLONG：按行发子调用，上千次，最终答对，花费 \$0.38，但作者认为用少得多的子调用也能做对。
- **E.4**，RLM(GPT-5) 做 CodeQA：900K Token 的代码仓，把代码分块交给子调用找线索，再用一次子调用汇总，答对，花费 \$0.27。作者特意说明：按块分派只在信息不密集的任务上可行。

### 做对的题基本是超集

Figure 9 逐题比较 RLM depth 1 与各基线：大多数情况下 RLM 做对的题覆盖了基线做对的题，并多做对一批，GPT-5 组尤其明显（PDF p. 40）。所以 Table 1 的提升主要是「多做对一些」，而不是「换了一批题做对」。

## 附录里其他值得知道的

**BrowseComp-Plus 的文档数扩展（附录 D.2）。** 在 150 题里随机抽 20 题，把给的文档从 10 篇加到 1000 篇（PDF p. 30）。只有 RLM 与 ReAct 这类迭代方法在 100 篇以上还能保持像样的表现；RLM(GPT-5) 是唯一在 1000 篇时满分的方法，去掉递归的版本约 90%。成本随文档数大致按对数线性增长，比 ReAct + BM25 更有界；按「GPT-5 窗口无限大」外推的直接读成本，还高于 RLM（PDF p. 30）。

**提示词（附录 C.1）。** 附录完整列出了每种方法的系统提示，所有任务共用一份（PDF p. 18–23）。RLM 的提示词大意是：你有一个 `context` 变量和一个能处理约 500K 字符的 `llm_query` 函数；REPL 的输出会被截断，所以要把想分析的东西交给子调用、用变量当缓冲区；要确保看完整个 context；先看材料、定切分策略，再逐块问、最后汇总。提示里附了几段示例代码：按章节迭代读一本书、把材料切成 10 份分别问再汇总、按 Markdown 标题切分。几个变体只是在此基础上改几行：

- Qwen3-Coder 版加一段「控制子调用次数、尽量成批」的警告（PDF p. 19）；
- depth 大于 1 时多一个 `rlm_query(context, query)`，会启动一个自带 REPL 的完整 RLM 循环，达到最大深度时自动退化为 `llm_query`（PDF p. 19–20）；
- Qwen3-8B 版把窗口与子调用容量都改成约 32K Token（约 100K 字符）（PDF p. 20）。

**压缩基线的成本（附录 C.2）。** GPT-5 组用 GPT-5-nano 做摘要，这解释了 Table 1 里 BrowseComp-Plus 上 Qwen3-Coder 的压缩 agent 平均成本是 GPT-5 组的近 15 倍；作者在 20 题小样本上确认 GPT-5 与 GPT-5-nano 做摘要的效果相当（PDF p. 24）。

## 负结果与限制

附录 B 列了五条「试过但不行」（PDF p. 17）：

1. **所有模型共用一份系统提示有问题。** 为 GPT-5 写的提示词直接给 Qwen3-Coder 用，会导致子调用过多，必须加一句限制。
2. **编码能力不够的小模型当不好 RLM**，如未经训练的 Qwen3-8B。
3. **思考 Token 过多的模型会撑爆单次输出上限。** 试过 Qwen3-235B-A22B 当 RLM，OOLONG 从 30% 升到 38%，提升小于主实验的模型，原因是不少轨迹的思考部分超过了单次调用的最大输出长度。
4. **没有异步子调用就很慢。**
5. **区分最终答案与中间想法很脆弱**，靠 `FINAL()` 与 `FINAL_VAR()` 标签，模型有时会把计划当答案交。作者认为训练原生 RLM 后这类问题应当消失。

第 7 节的限制（PDF p. 9）：更难、更自然的长上下文任务评测还很少；RLM 的护栏怎么做还没研究；多了一层复杂度，可能带来子调用成本失控之类的副作用；异步子调用与沙箱化的 REPL 能省时省钱，但会让系统更复杂。

**我们读完要留下的判断：**

- **支撑最强的结论**：把材料放进变量、用代码驱动子调用，在信息密集的长上下文任务上明显好于直接读和常见支架，且平均成本同量级。GPT-5 组的 Table 1、Figure 1、Figure 9 三方面互相印证。
- **只算初步证据的结论**：训练原生 RLM 能快速见效。只有 8B 与 4B 两个点，一个是蒸馏，一个是单任务强化学习。
- **表述上要打折的**：摘要的三个中位数（其中一个是跨模型比较）、OOLONG 的 28.4%（按表是 27.3%）、RLM-Qwen3-8B「接近 GPT-5」。
- **没有给的**：安全与护栏；并行子调用下的实际耗时；Qwen3-Coder 组之外，其他开源模型作为根模型时的稳定性；任务无关的最优切分策略。

## 它和其他长上下文路线的关系

第 6 节把长上下文系统分成两个正交方向：改架构、重新训练基座；或者在模型外搭支架。RLM 属于后者（PDF p. 9）。在支架这一支里，它与压缩、截断这类「有损上下文管理」不同，也与在支架里显式建一套记忆层级（MemGPT、Mem0 之类）不同：RLM 的上下文管理全部由模型自己通过代码隐式完成（PDF p. 9）。

在「用子调用分解任务」这一支里，ViperGPT、THREAD、ReDel、Context Folding、AgentFold 都让模型自己决定子调用，但处理不了超过基座窗口的输入；DisCIPL 一次性生成带子调用的程序，出错不能回头改。RLM 的区别在于 prompt 放在外部环境里，并能靠持久 REPL 的执行反馈迭代修正（PDF p. 9）。

站内相关篇目（外部补充，不是本文依据）：把长上下文做便宜的架构路线见 DeepSeek-V3.2 一篇；用多轮强化学习训练记忆 agent 处理长上下文见 MemAgent 一篇；长上下文里位置偏差的经典现象见日常研读的 Lost-in-the-Middle 一篇。

## 可迁移启发

1. **先拆掉「一次调用必须看见全部输入」的假设。** 长材料进变量，模型只拿元数据。这一步本身就能把超窗口任务从 0 分拉到可用，OpenCode 与 Claude Code 的「放文件」版本已经证明了这一点。
2. **子调用要能被程序触发，而不只是被模型口头发起。** 能在循环里对每一片、每一对调用模型，才能做 $O(N)$ 与 $O(N^2)$ 的语义工作。
3. **长输出也走变量。** 答案在代码里拼好再整体返回，就不受单次生成长度约束。但要给模型一个可靠的交卷机制，否则会出现 E.2 那种「答案在手却不交」。
4. **根模型的历史只放常数大小的东西。** stdout 只回前缀与长度，逼模型用变量管理中间结果；这条比看起来重要。
5. **递归深度与子调用次数是放大器，两个方向都会放大。** 对 GPT-5 越深越好，对 Qwen3-Coder 越深越糟。上线前要按根模型测深度，并给子调用次数设预算。
6. **训练可以只对准根策略，而且可以用无关领域的数据。** 叶子就是普通 LLM 请求，门槛是学会切、学会分派。蒸馏时要用程序修补模板错误。
7. **报成本时把中位数、均值和尾部分开。** RLM 的中位数便宜，尾部很贵；只报均值或只报中位数都会误导。
8. **长推理也可以外置中间状态。** 「调度、记账、核对由根模型做，求解交给子调用，答案存进字典」这一套，把 LongCoT-mini 从 38.7 做到 65.6。

## 关键词回看

- **RLM**：把 prompt 放进 REPL 变量、用代码递归调用模型的推理期支架，对外仍是字符串进、字符串出。
- **三个设计选择**：prompt 进变量、答案从变量出、子调用由代码触发。缺一个，上限就被窗口或单次输出锁住。
- **stdout 只回元数据**：根模型每轮最多多出常数个 Token，最多跑 $K/c$ 轮，每轮可发起任意多子调用。
- **depth 0 / 1 / ≥2**：只有 REPL；可调普通 LLM；可调子 RLM。depth 0 回答「REPL 本身值多少」。
- **复杂度随长度**：S-NIAH 是 $O(1)$、OOLONG 是 $O(N)$、OOLONG-Pairs 是 $O(N^2)$。越密的任务，直接读掉得越早。
- **26% / 130% / 13%**：GPT-5 为底相对压缩、CodeAct + 子调用、Claude Code（放文件版，Opus 4.1）的四任务中位提升。
- **RLM-Qwen3-8B**：约 1000 条无关领域蒸馏轨迹、300 步、48 个 H100 小时；相对同支架未训练版中位 +28.3%，耗时降 68%–90%。
- **第一次分解**：系统提示里的例子能显著改善它，哪怕例子与任务无关。
- **Orchestrate; don't solve**：LongCoT-mini 分解提示的核心，根模型只调度、记账、核对。

# 序列打包

一句话:序列打包要解决的是**把长短不一的文档装进固定长度的训练序列**。逐条 padding 浪费算力,先拼接再切段会把文档切断,best-fit 装箱几乎两头都不吃亏;装进同一条序列的文档还得用文档掩码互相隔开。装法选定后,每一步的数据分布、每个 token 的损失权重、MoE 的路由负载都会跟着变,这些账要一起算。

## 一、为什么要打包:padding 的浪费与截断的代价

训练时一个 batch 是形状固定的张量,每一行都是长度 $L$ 的序列(预训练常见 4K–8K,长上下文阶段到 128K 以上)。真实文档的长度却是长尾分布:大多数网页只有几百 token,少数书籍和代码仓库动辄几十万 token。Trinity Large 的报告把它描述为对数正态分布(Trinity-Large PDF p. 9)。形状固定、长度参差,必须找个办法把文档「装箱」。

**最朴素的做法是一条文档占一行,不够的补 padding。** padding 是专门用来占位的无意义 token,不算损失,但照样占着矩阵乘和注意力的计算。设一共 $N$ 行,每行长 $L$,文档 $d$ 的长度为 $|d|$:

$$
\text{padding 率}=1-\frac{\sum_d |d|}{N\cdot L}
$$

意思是:花出去的 $N\cdot L$ 个位置里,有多大比例在算空气。Krell 等人统计过常见 NLP 数据集,**最多有 50% 的 token 是 padding**,GLUE-cola 这种短句数据按 128 长度补齐时高达 89%(Efficient Sequence Packing without Cross-contamination)。像订了一排大巴座位,每个乘客单独坐一辆车。

**省掉 padding 的直觉做法是先把所有文档首尾相接,再按 $L$ 一刀一刀切**(concat-then-split,拼接切段)。padding 率是零,代价是大量文档被切断。Ding 等人的统计里,绝大多数文档本来就短于 2048 token、完全装得进一行,拼接造成的截断恰恰主要落在这些短文档上(Fewer Truncations Improve Language Modeling p. 5–6)。切断带来两种伤害:

- **后半截没了开头**:模型被要求续写一段看不到前文的文字,只能凭空补出前文里本该有的事实,这是在训练「无依据地编」。Qwen3-Coder-Next 的报告把这叫 context hallucination(上下文幻觉,PDF p. 19)
- **开头决定格式的数据伤得最重**:Agent 轨迹的工具定义和调用格式只写在开头,被切到上一行之后,模型看得到调用却看不到定义。Qwen3-Coder-Next 的实验数据里,拼接切段把 30.2% 的文档切成了碎片(Qwen3-Coder-Next PDF p. 19–21,Table 13)

于是出现两难:**不切就得留空位,不留空位就得切**。另外还有第三个问题:同一行里装了好几篇文档,后一篇的 token 能不能注意到前一篇?这就是第二节的文档掩码。

## 二、三种装法与文档掩码

### 三种装法长什么样

用一个 $L=8$ 的小例子,4 篇文档长度分别是 A=5、B=6、C=3、D=2(`·` 是 padding):

```text
逐条 padding  [A A A A A · · ·][B B B B B B · ·][C C C · · · · ·][D D · · · · · ·]  空位 16/32
拼接切段      [A A A A A B B B][B B B C C C D D]                                    B 被劈成两半
best-fit 装箱 [B B B B B B D D][A A A A A C C C]                                    不切、不空
```

**best-fit packing(最优适配装箱)把打包看成经典的装箱问题**:每篇文档是一件物品,每条训练序列是一个容量为 $L$ 的箱子。算法是 Best-Fit-Decreasing:文档按长度从大到小排,每篇放进「剩余空间最小但仍装得下」的那个箱子,都装不下才开新箱。超过 $L$ 的文档先预切成不超过 $L$ 的块,这是上下文长度逼出来的最小截断。为什么这样装得满?因为语料里绝大多数文档远短于 $L$,大量小物品很容易把大物品留下的缝隙填满。Ding 等人用线段树把查找做到 $O(N\log L)$,在 2K 与 8K 长度、自然语言与代码数据上,多出来的训练序列都不超过 0.01%,效率和拼接切段几乎一样(Fewer Truncations p. 5)。

### 同一份数据换五种装法

Qwen3-Coder-Next 在 SWE-bench 的 agentless 设置上对比了几种装法,两个折中变体是在拼接切段上做最小改动:**RLD**(restart last document)让被切断的末篇文档在下一行从头重来,消掉头部截断,但尾部照样切,而且长文档的开头被反复训练,悄悄加了权;**PLD**(pad last document)干脆把放不下的末篇整篇挪走、空位补 padding,彻底不切,但 padding 率冲到 17.55%,为了公平只能把训练 token 按 $1/(1-\text{padding 率})$ 放大(Qwen3-Coder-Next PDF p. 20–21)。

| 装法 | 训练 token | 碎片率 | padding 率 | 平均相似度 ↑ | 空补丁率 ↓ |
|---|---|---|---|---|---|
| 拼接切段 | 73B | 30.2% | 0 | 16.68% | 38.94% |
| RLD | 73B | 17.8% | 0 | 17.24% | 35.84% |
| PLD | 89B | 0 | 17.55% | 16.86% | 34.44% |
| best-fit | 73B | 0 | 0.01% | 17.82% | 36.26% |
| best-fit + 超长文档预切 | 73B | 0 | 0.01% | 20.17% | 25.01% |

数据来自 Qwen3-Coder-Next PDF p. 21 Table 13。三点结论:**消掉碎片本身就涨点**,best-fit 在相似度与空补丁率上都赢拼接切段;**best-fit 比补 padding 省 token**,73B 对 89B 效果还更好(空补丁率一项 PLD 略优);**超长文档怎么处理同样要紧**,给 best-fit 加上预切、滑窗或直接丢弃后提升最大,丢弃最好(20.84%、24.34%),主实验采用预切。Qwen3-Coder-Next 正式训练就用 best-fit,上下文开到 262,144 token(PDF p. 5–6)。

### 文档掩码:同一行里的文档互相看不见

普通的因果掩码只要求「不看未来」,打包之后还要加一条「不看别的文档」:

$$
M_{ij}=\begin{cases}0, & \mathrm{doc}(i)=\mathrm{doc}(j)\ \text{且}\ j\le i\\ -\infty, & \text{否则}\end{cases}
$$

意思是:位置 $i$ 只能注意同一篇文档里、不晚于自己的位置 $j$。整条序列的掩码变成沿对角线排开的一串小三角,每篇文档的计算都和它单独成行时一样。这个掩码和因果掩码、padding 掩码加在同一个地方(softmax 之前),合并规则也一样,任一条要求屏蔽就屏蔽。

**实现上不必真造一个 $L\times L$ 的掩码矩阵。** 变长注意力 kernel(如 FlashAttention 的 varlen 接口)把一行里的文档当成紧凑拼接的多条序列,只额外传一个累积长度数组 `cu_seqlens`:上面 best-fit 第一行是 B、D 两篇,`cu_seqlens = [0, 6, 8]`,kernel 据此跳过跨文档的块。附带的好处是注意力计算量从 $L^2$ 降到 $\sum_d |d|^2$;Ding 等人实测这种按文档分块的注意力和整段注意力相比看不出额外开销(Fewer Truncations p. 19)。kernel 侧的入参与分块细节见 FlashAttention 篇。

**位置编号要不要每篇重置为 0?** RoPE 只依赖相对位置,理论上不重置也等价,Ding 等人就没改位置编号(p. 19);Laguna 则在文档边界重置位置编号,理由是避免文档掩码下与 RoPE 相关的舍入误差(Laguna PDF p. 6)。用绝对位置编码的模型必须重置,否则第二篇文档从位置 6 起步,学到的位置含义就错了。

### 掩码和装法是两件事

最容易混的一点:**加了文档掩码不等于解决了截断**。Ding 等人专门拆开做过消融(2K 长度,自然语言):

| 装法 | 文档掩码 | 困惑度 | 阅读理解 | 上下文遵循 | 摘要(ROUGE-2) |
|---|---|---|---|---|---|
| 拼接切段 | 无 | 9.64 | 46.71% | 40.60% | 12.16 |
| 拼接切段 | 有 | 9.53 | 47.92% | 42.41% | 11.79 |
| best-fit | 有 | 9.53 | 48.92% | 46.30% | 13.14 |

数据来自 Fewer Truncations p. 19 Table 10。**困惑度的收益来自掩码,下游任务的收益主要来自不切断**;只给拼接切段加掩码,摘要反而掉了。原因很直白:掩码能挡住别的文档的干扰,但被切掉的前文找不回来。

公开配方的选择并不统一,说明这是一个「看阶段、看代价」的决定:

| 模型 | 做法 | 出处 |
|---|---|---|
| Llama 3 | 预训练就加跨文档掩码;标准预训练里影响有限,在超长序列的继续预训练里很重要 | Llama-3 PDF p. 6 |
| DeepSeek-V3 | 参照 Ding 等人做 document packing 保证数据完整,但**不加**跨样本掩码 | DeepSeek-V3 PDF p. 22 |
| Olmo 3 | 预训练与中训用拼接切段;扩上下文时改 best-fit,并加文档内掩码 | Olmo-3 PDF p. 34–35 |
| Trinity | Nano、Mini 不加文档掩码,Large 加 | Trinity-Large PDF p. 9 |

## 三、细节与常见坑

### loss 口径:按 token 平均还是按文档平均

打包之后「一行」不再等于「一条样本」,损失怎么归一化要重新说清楚。设 $m_t$ 为有效标签掩码(padding、SFT 里的提示词取 0),$\ell_t$ 为位置 $t$ 的交叉熵,$D$ 为文档数:

$$
\mathcal L_{\text{token}}=\frac{\sum_d\sum_{t\in d} m_t\,\ell_t}{\sum_d\sum_{t\in d} m_t}
$$

这是按 token 平均:每个有效 token 权重相同,长文档、长回答贡献的梯度按长度成正比放大。

$$
\mathcal L_{\text{doc}}=\frac{1}{D}\sum_d\frac{\sum_{t\in d} m_t\,\ell_t}{\sum_{t\in d} m_t}
$$

这是按文档平均:先在每篇文档内部平均,再让每篇等权,短样本的每个 token 权重更大。两种都合法,要显式选。**真正的坑是第三种没人选过的口径**:

- **按行平均**:先对每一行求平均再平均各行。一行里装了几篇、每篇有几个有效 token 全看装箱的运气,于是同一个 token 的权重取决于它和谁被装进了同一行。预训练里各行几乎装满,影响小;SFT 只算回答 token,各行有效 token 数相差很大,口径就被装箱悄悄改了
- **按微批平均再平均**:梯度累积和数据并行时,先在每个微批内按 token 平均、再把各微批取平均,不等于全局按 token 平均,因为各微批的有效 token 数不同。正确做法是先把各微批的损失求和,再除以全局有效 token 总数
- **padding 要从分子分母里同时去掉**。PLD 的 padding 就是屏蔽梯度的(Qwen3-Coder-Next PDF p. 20);只屏蔽分子、分母还数着 padding,等于按每批 padding 的多少给损失打折,padding 多的批次被悄悄降了权

打包方式和批大小一变,每步真正更新的样本数、token 数跟着变,warmup 和衰减长度要对应回 token 预算,见 优化器 篇。

### SFT 与多轮对话:打包必须隔离注意力

SFT 样本普遍很短,不打包会浪费大量算力,所以 SFT 同样要打包,而且**隔离要求比预训练更硬**。预训练里跨文档注意力只是噪声,SFT 里它是泄漏:后一段会话能读到前一段会话的问题和答案,模型学到「答案可以从上文另一个用户那里抄」;推理时上文没有别人的会话,训练和推理的输入分布对不上。

**只加分隔符挡不住。** 分隔符只是序列里的一个 token,注意力照样能越过它读到前面所有内容;要挡住必须改掩码,也就是上一节的文档掩码或 varlen 接口。打包 SFT 时还有三件事要检查:每条样本的标签掩码按它自己的角色边界算,不能跨样本错位;每段的第一个目标 token 不能拿上一段的最后一个位置去预测;loss 口径按上一小节显式选定。SFT 模板、角色掩码与多轮历史怎么组织见 SFT 篇。

### 批间异质性:在线顺序打包的隐患

边读边分词、按顺序装箱时(TorchTitan 这类框架的做法),一篇长度是 $L$ 好几倍的文档会被连续续进下一行、下一个批次。文档长度是对数正态分布,少数超长文档就会让连续几步的 batch 都偏向某一个领域。Trinity 的判断是:**每一步都像在优化一个略有不同的目标分布**,网络每步都要把上一步的偏差「忘掉」;而且这是顺序打包本身造成的,打乱文档顺序也消不掉(Trinity-Large PDF p. 9–10)。

衡量这件事,Trinity 定义了 BatchHet(批异质性):

$$
\text{BatchHet}_t=\max_i L_i^{(t)}-\frac{1}{M}\sum_{i=1}^{M}L_i^{(t)}
$$

$L_i^{(t)}$ 是第 $t$ 步第 $i$ 个微批的损失,$M$ 是微批数。意思是:这一步里最「偏科」的那个微批比平均水平差多少。它在小实验里和梯度范数的不稳定强相关。

对策是 **RSDB(随机顺序文档缓冲)**:整篇文档分词后放进缓冲区,各自带一个读头;填一行时随机挑一篇文档、从它的读头往下读,读满了就换下一篇随机文档,读头位置随之前移。它不预先切块,读是随机的,又不丢任何 token。小实验里 BatchHet 降了 46%,梯度范数的峰度从 187 降到 14.6;基线要把 batch 放大约 2 倍才追平逐步损失方差,放大约 7 倍才追平 BatchHet(PDF p. 10)。Trinity Large 在第三阶段接入 RSDB(报告 p. 9 说在该阶段开始前、p. 11 说在该阶段期间,两处不一),BatchHet 降到原来的 1/4.23,逐步方差降到 1/2.4(PDF p. 11)。**注意这组真实训练数字前后阶段的数据分布也变了**,报告自己说直接对比有难度。

### MoE 里的 padding:被路由的空气

装箱之后仍会留下一些 padding。在稠密模型里 padding 只是浪费;**在 MoE 里它还会参与路由**。Laguna M.1 打包后仍有约 5% 的训练 token 是 padding,它们照常被路由、还被计入负载均衡损失(Laguna PDF p. 9)。

为什么这会出事?padding 位置的语言模型损失被屏蔽,padding 的词嵌入学不到东西;在文档掩码下 padding 也不和周围 token 混合。于是**同一批里每个 padding 到达路由器时的表示完全相同**,全被送进同一个专家,可能把它打满,负载均衡损失又把这份假热点当真去纠正。Laguna XS.2 加了跳过 padding 路由与均衡统计的选项,消融确认更稳(PDF p. 9),辅助损失只在非 padding token 上统计(PDF p. 5)。负载均衡本身的机制见 MoE路由 篇。

文档掩码还会带来另一种不均衡:注意力计算量是 $\sum_d |d|^2$,装了一篇长文档的行比装满短文档的行重得多。Llama 3 为此在流水线并行里改用异步点对点通信,上下文并行选 all-gather 方案也是因为它容易支持文档掩码这类不规则掩码(Llama-3 PDF p. 11);长上下文阶段按注意力面积均衡负载的做法见 长上下文训练 篇。

### 长上下文阶段:天然长文档胜过拼出来的长序列

扩上下文时,用短文档拼满 128K 最省事,但拼出来的序列里没有真正的长依赖。Phi-4 从 4K 扩到 16K 时做过对比,**天然长文档在长上下文任务上好过把短样本拼满序列的人造长样本**,于是专门筛出 8K 以上的学术、书籍、代码数据,并给 16K 以上的子集加权(Phi-4 PDF p. 10)。

装法在这个阶段也被放大。Olmo 3 发现,扩上下文时继续用拼接切段,训练样本的平均长度比文档本身的长度分布还短,长文档被切碎,长上下文恰恰学不到;改成 best-fit 后在更长的长度上 RULER 明显更好,再配上文档内掩码防止跨文档的虚假注意力模式(Olmo-3 PDF p. 32、p. 34–35)。Llama 3 也说文档掩码在超长序列的继续预训练里才真正重要(PDF p. 6)。三条放在一起:**长上下文阶段要的是完整的长文档,装法要保长、掩码要隔开**。RoPE 扩窗、长度分阶段这些手段见 长上下文训练 篇,语料配比见 数据工程 篇。

## 四、对比与选型

| 装法 | padding | 截断 | 跨文档干扰 | 主要代价 | 适合 |
|---|---|---|---|---|---|
| 逐条 padding | 高(常见数据可达 50%) | 只截超长 | 无 | 算力浪费 | 评测、极小规模实验 |
| 拼接切段 | 0 | 大量 | 有(不加掩码时) | 上下文幻觉、切断工具定义 | 语料极短且格式无所谓时的大规模预训练 |
| 拼接切段 + 文档掩码 | 0 | 大量 | 无 | 困惑度改善,但切掉的前文找不回 | 过渡方案 |
| RLD / PLD | 0 / 较高 | 仅尾部 / 无 | 取决于掩码 | RLD 给长文档开头加权;PLD 浪费 token | 框架改动受限时 |
| best-fit + 文档掩码 | 约 0.01% | 只截超长 | 无 | 需要离线装箱与 varlen kernel | 预训练、代码与 Agent 数据、长上下文、SFT |
| 在线顺序打包 + RSDB | 约 0 | 在线续读 | 取决于掩码 | 缓冲区内存 | 边读边分词的超大规模流水线 |

怎么选,按三个问题走:

1. **数据的开头重不重要?** 代码、Agent 轨迹、SFT 对话的开头定义了格式和条件,不能切,用 best-fit
2. **能不能加文档掩码?** 有 varlen kernel 就加,SFT 必须加;预训练里不加也能训(DeepSeek-V3 就没加),但越长越该加
3. **在线还是离线?** 离线能先分词再装箱,用 best-fit;只能在线流式处理的,至少用 RSDB 这类随机缓冲把批间异质性压下去
